# Rush v0.2 Expansion Implementation Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** Expand Rush from five Python/JS quality tools into a multi-language, engine-discovery-first code-quality platform with the documented v0.2 tool catalog, while preserving one canonical implementation per tool for CLI and stdio MCP.

**Architecture:** Keep Rush as a thin orchestration layer around externally discoverable engine CLIs. First replace the fixed five-tool assumptions with metadata-driven tool/engine registries, generic routing, canonical aggregation, and reusable CLI/MCP registration. Then add engine adapters in independently testable capability batches: static quality, content/IaC, supply-chain/security, test quality, developer workflow, language ecosystems, Graft context, and semantic-drift testing.

**Tech Stack:** Python 3.12, uv, Click, Rich, FastMCP (`mcp`), pytest, Ruff, pip-audit, GitHub Actions; optional Python engine extras; externally discovered CLIs for Go, Rust, Node, Docker, Terraform, .NET, Java, and other language ecosystems.

## 1. Current Context and Non-Negotiable Assumptions

- Current public repository: `https://github.com/jamesdsizemore/rush-cli`.
- Current branch is `main`; v0.1 through Phase 7 are complete and remote CI is green.
- Current baseline is **50 passing tests** via:
  ```bash
  unset VIRTUAL_ENV PYTHONPATH
  .venv/Scripts/python.exe -m pytest tests/ -q
  ```
- `research/` is local/untracked and must remain excluded from commits.
- v0.1 currently hardcodes five tools in:
  - `src/rush/tools/__init__.py`
  - `src/rush/cli.py`
  - `src/rush/mcp.py`
  - `src/rush/tools/base.py`
  - `tests/test_mcp.py`
- The source architecture documents the candidate v0.2 catalog in `findings.md:69-133` and language matrix in `findings.md:95-120`.

### Must remain true in v0.2

1. MCP remains **stdio only**. Do not introduce HTTP, SSE, ports, authentication, a daemon, or a separate SDK.
2. MCP stdout remains JSON-RPC only. Logs remain stderr NDJSON.
3. CLI and MCP invoke the same `ToolFn.run()` / `ToolFn.__call__()` implementation.
4. Every result remains a JSON-serializable canonical `ToolResult`.
5. Missing engines return structured `status="skipped"`; they never crash Rush.
6. Rush does not import code from `headcleaner` or Graft.
7. Engine binaries are **not** required runtime dependencies. Optional extras may install Python-native engines for convenience, but every engine must still be independently discoverable on `PATH`.
8. `review` remains deterministic by default; cloud/LLM review remains opt-in and is not part of this v0.2 plan.

### v0.2 target catalog

Implement the documented v0.2 backlog in staged groups:

- **Static/code quality:** `typecheck`, `dead`, `complexity`, `slop`.
- **Repository content and infrastructure:** `markdown`, `actions`, `yaml`, `sql`, `templates`, `containerfile`, `iac`.
- **Security/supply chain:** `secrets`, `sbom`.
- **Test quality:** `coverage`, `mutation`, `e2e`, `pbt`, `visual`, `snapshot`, `flaky`, `fuzz`, `load`, `contract`.
- **Developer workflow:** `commit-msg`, `ci`, `release` and optional pre-commit integration.
- **Language routing:** Go, Rust, Ruby, Java, Kotlin, Swift, PHP, C#, Elixir, Dart/Flutter, Scala, and Nix in addition to existing Python and JS/TS.
- **Context/testing extensions:** optional Graft-backed review context and semantic-drift detection.

Explicitly deferred from this plan: cloud AI review, OSV as a security-engine replacement, licensing/compliance, additional HTTP transport, C/C++/Haskell/Lua support, and automatic publishing.

## 2. Dependency and Distribution Policy

### Runtime dependencies

Do **not** add all engines to `[project.dependencies]`. Rush must remain installable and usable without Node, Go, Rust, Java, Docker, Terraform, or .NET.

Keep runtime dependencies limited to Rush itself:

```toml
[project.dependencies]
# mcp, click, rich, pytest only when Rush continues to own its test runner
```

### Development dependencies

Keep repository-quality tooling in `dev`, pinning every version used by CI:

```toml
[project.optional-dependencies]
dev = [
  "pip-audit==...",
  "ruff==...",
  "pytest==...",
]
```

### Optional engine bundles

Introduce convenience extras by ecosystem, each clearly documented as optional:

```toml
[project.optional-dependencies]
python-engines = [
  "coverage==...",
  "djlint==...",
  "mypy==...",
  "radon==...",
  "sqlfluff==...",
  "vulture==...",
]
security-engines = [
  "checkov==...",
]
all-python-engines = ["rush-cli[python-engines,security-engines]"]
```

Do not add a non-Python executable to an extra just to imply that Rush installs it. Instead document a per-engine install command in the engine metadata:

| Engine class | Installation behavior |
|---|---|
| Python CLI | Optional Rush extra and documented `uv tool install` / `pipx` option |
| npm/npx CLI | Project-local `npm install -D` or global `npm install -g` guidance |
| Go/Rust/Haskell binary | Platform package manager / release binary guidance |
| Docker/terraform/.NET tool | Existing host prerequisite; return `skipped` if absent |

## 3. Proposed Core Design

### 3.1 Replace fixed tool names with runtime metadata

`ToolName = Literal[...]` in `src/rush/tools/base.py` cannot scale to 30+ independently registered tools. Replace the fixed literal with a string alias and validate tool names at registry construction.

Create `src/rush/catalog.py` containing immutable metadata:

```python
@dataclass(frozen=True)
class ToolSpec:
    name: str
    category: Literal["quality", "security", "test", "workflow"]
    description: str
    mcp_description: str
    engine_names: tuple[str, ...]
    supports_path: bool = True
    experimental: bool = False

@dataclass(frozen=True)
class EngineSpec:
    name: str
    binary: str
    install_hint: str
    file_extensions: tuple[str, ...]
    project_markers: tuple[str, ...]
    capability: Literal["lint", "format", "test", "security", "metrics", "workflow"]
```

Use a single `TOOL_SPECS` map and a single `ENGINE_SPECS` map. The registry validates that each concrete tool has exactly one spec and that each referenced engine exists.

### 3.2 Extend canonical results without breaking v0.1 clients

Retain existing required result keys. Add only optional keys to `ToolResult`:

```python
class ToolResult(TypedDict, total=False):
    # existing keys stay unchanged
    tool: str
    engine: str | None
    engine_version: str | None
    status: ToolStatus
    duration_ms: int
    summary: str
    findings: list[Finding]
    raw: Any | None

    # v0.2 optional extensions
    metrics: dict[str, int | float | str]
    artifacts: list[str]
    metadata: dict[str, Any]
```

Examples:
- `coverage` sets `metrics={"line_percent": 84.2, "branch_percent": 76.0}`.
- `sbom` sets `artifacts=["bom.json"]`.
- `release` sets `metadata={"tag": "v0.2.0", "published": False}`.

### 3.3 Build reusable aggregation and routing

Extract current per-tool status joining (`_combine_status`) and file collection from `src/rush/tools/lint.py` into a shared routing module. It must:

- determine files once;
- ignore generated/vendor directories deterministically;
- group files by engine capability and extension;
- run each selected engine once;
- combine statuses by a documented severity rank;
- concatenate findings in stable path/line/rule order;
- merge metrics and artifact paths without overwriting;
- return a `skipped` result only when no installed eligible engine can run.

### 3.4 Standardize engine adapters

Use the existing `Engine` ABC in `src/rush/engines/base.py` and `tools/common.py:run_engine()` as the only subprocess gateway. Add parser helpers for common report families:

- JSON list/object reports;
- SARIF reports;
- JUnit XML reports;
- Cobertura/LCOV coverage reports;
- text-only exit-code reports.

Each engine adapter owns only:

1. argv construction;
2. engine-specific output parsing;
3. native severity to Rush severity mapping;
4. normalized findings/metrics/artifact extraction.

### 3.5 Dynamic CLI and MCP registration

Refactor `src/rush/cli.py` to register all path-based tools from `ALL_TOOLS` rather than hand-writing 27 more Click functions. Preserve dedicated typed commands only for tools with additional flags (`review --llm`, `format --check`, `release --dry-run`, etc.).

Refactor `src/rush/mcp.py` so it continues iterating `ALL_TOOLS`; update its server instructions dynamically from the catalog instead of hardcoding “Five tools.”

Every new MCP tool must use the `rush_<tool-name>` namespace and describe skip behavior in fewer than 200 characters.

## 6. Risks and Tradeoffs

| Risk | Mitigation |
|---|---|
| 27 tools become unmaintainable | Build catalog/routing/parser infrastructure before adding adapters; ship in capability batches with independent commits. |
| Bundling every engine makes Rush fragile | Keep engine discovery; use optional extras only for Python-native developer convenience. |
| Slow, destructive, browser, fuzz, load, or release actions surprise users | Require explicit opt-in flags and default to analysis/dry-run/`skipped`. |
| MCP schemas drift from CLI | Test live stdio server registry parity and retain a shared ToolFn implementation. |
| External engine output formats change | Store sanitized fixture reports and unit-test parsers separately from real-engine smoke tests. |
| CI becomes expensive | Core fixture CI on every PR; small representative real-engine matrix; avoid installing all foreign runtimes. |
| Secret scanner leaks material | Never retain values in normalized results, `raw`, logs, fixtures, or failure output. |
| Scope conflict: semantic drift is listed as v0.2 in one backlog and v0.3 in another | Treat it as experimental and gate implementation behind explicit config/flags. |
| Config complexity grows | Start with validated `tomllib` mappings; introduce Pydantic only with a measured validation need. |

## 7. Open Questions to Resolve Before Implementation

1. Does “all other dependencies” mean install every Python engine in `rush[all-python-engines]`, or only add engine metadata/install guidance while preserving a lean default install?
2. Should all 27 backlog entries be a single `0.2.0` release, or should capability batches become `0.2.0` through `0.2.x` milestones under one v0.2 program?
3. Which tools are permitted to execute network-facing actions (`load`, `contract`, `release`, TruffleHog verification), and should they all require a global `--allow-network` flag?
4. Should Graft integration use a local CLI invocation, a configured MCP bridge, or only consume a prebuilt local graph? The default recommendation is an optional local CLI/provider abstraction with no remote calls.
5. Should semantic drift remain experimental in v0.2, given its .NET/Playwright prerequisite and potential browser side effects?
6. What v0.2 versioning target is desired: `0.2.0-alpha`, `0.2.0-beta`, or a sequence of prereleases?

- full project-v​​env gates, dependency audit, package build, clean-clone install, and remote GitHub Actions pass;
