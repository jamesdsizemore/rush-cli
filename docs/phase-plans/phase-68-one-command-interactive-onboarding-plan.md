# Phase 68 — One-and-Done Install

## 1. Why this phase exists

Real end-to-end testing this session (2026-09-13/14) found the actual path from "download rush" to "rush is checking my code" requires four separate typed commands, each with flags never documented anywhere a new user would find them:

```
curl -fsSL .../install.sh | sh
rush init .
rush governance sync
rush setup . --install --allow-download --allow-network --allow-build --allow-cache-write
```

Explicit requirement from the maintainer, verbatim, final: a user should only ever have to run one command (the install line itself, or `rush install` — never longer than two words) or click one button. That single action installs into the current project, activates and serves the MCP server, activates and serves all available CLIs, activates and serves the memory system, and launches the web dashboard. No picker, no prompt, no second command, no wizard.

**Extended requirement (2026-09-14):** the dashboard must stay reachable without the user doing anything again — not after closing the terminal session, and not after restarting the machine, including before that user logs back in. `rush install` registers a real, boot-level OS autostart entry: a `LaunchDaemon` on macOS (`/Library/LaunchDaemons/`, `RunAtLoad` true, runs as the installing user via `UserName`, not root), a system-level `systemd` unit on Linux (`/etc/systemd/system/`, `enabled --now`, `User=` the installing user), and a Windows Scheduled Task with an `ONSTART` (boot) trigger running as the installing user. Registering any of these three requires one elevated-privilege prompt during `rush install` (`sudo` on macOS/Linux, a UAC prompt on Windows) — that elevation is scoped to this one registration step, not the rest of install. The TUI (`rush ui`) is not part of this — it is a foreground interactive terminal program; there is nothing sensible to "autostart" about it. Only the headless dashboard server gets a persistent, boot-level autostart entry.

**Extended requirement (2026-09-14, round 2):** the install experience itself must be graphic, animated, engaging, and explanatory — a live, styled progress display naming each step as it runs (registering the project, detecting the stack, writing config, syncing governance, installing engines, connecting agents, launching the dashboard, registering boot autostart), not a plain scrolling log. This does not reopen line 14's "no picker, no prompt, no second command, no wizard" requirement: the whole run is still fully automatic and non-blocking end to end, including through `curl | sh` — piping a script into `sh` or a downloaded `pwsh` binary cannot read an interactive prompt from stdin regardless of what gets built here (established in the original research below), so nothing in this phase ever waits on typed input. The one real, unavoidable place a human has to act is the OS's own elevation dialog (`sudo`/UAC) for boot-autostart registration — P68-05 explains what that's for and why, in the animated display, immediately before the OS raises it; the OS dialog itself remains the actual consent gate, not a second custom prompt layered on top of it.

## 3. Scope

**In scope:** `rush install` (both as the installer scripts' handoff and as the command an existing install re-runs) does everything in one shot when run from inside a project directory with no arguments: registers the current directory as the project, detects its stack, writes `rush.toml`, syncs governance rules, installs missing engines, starts serving the MCP server, connects every detected agent's CLI, activates memory, launches the web dashboard, and registers a real, boot-level OS autostart entry for that dashboard on macOS, Linux, and Windows (one elevated-privilege prompt scoped to that single registration step) — all in the one command, no follow-up command, no separate install path. The entire run displays as a live, styled, explanatory Rich progress sequence naming each step, reusing `THEME`/`MOTION` from `src/rush/dashboard/theme.py`, never blocking on typed input anywhere. A companion `rush uninstall` removes exactly that autostart entry and stops the running service.

**Out of scope, explicitly not touched here:** the `--allow-*` permission-flag architecture shared by the other ~29 CLI commands (`permission_options` in `src/rush/cli_support/options.py`) — unrelated commands keep their existing flags. `rush setup`, `rush init`, and `rush governance sync` remain available as standalone commands for anyone who wants to run a piece manually or script it (e.g. in CI) — this phase makes `rush install` do all of it automatically, it does not remove the individual commands. `rush ui` (the TUI) is never autostarted — no headless mode exists for it, and a foreground terminal program has nothing to "start in the background." `rush uninstall` removes only the autostart registration this phase adds — it never deletes registered projects, `rush.toml`, or memory data; a full data-wipe uninstall is a separate, unasked-for capability.

## 5. Dependencies and completion

Depends on: Phase 65 (`rush install`, `rush ui`, `rush setup`, MCP server all already implemented and shipped), this session's `e74995d` (`rush setup --install` PyPI fix) and `e03791f`/`d898178` (PATH-persistence fixes in both install scripts) — all already on `main`. **P68-05 (boot-level autostart) additionally depends on Phase 69's P69-01 (HTTP/session security hardening) landing first** — P68-05 makes the dashboard server run unattended, at boot, indefinitely, before Phase 66's own §0 reconciliation found that same server had no CSP header, no rate limiting, plaintext session secrets, and a mutation-replay gap across projects; shipping boot-persistence before those close means the vulnerable version is the one running around the clock. **P68-04 additionally depends on Phase 69's P69-03 (live map population and completeness) landing first** — P68-04 publishes its own install-triggered scan result through `ProjectRegistry.publish_scan_result`, the atomic snapshot/source_identity/sequence primitive P69-03 adds; that primitive has to exist before P68-04 can call it. P68-01 through P68-03, P68-06, and P68-07 have no such dependency and can proceed independently.

No self-update/version-check command exists in this repo today (checked: `grep -n "def update" src/rush/cli.py`, zero matches). This phase does not add one. A consequence worth naming, not solving here: if the installed binary is later replaced (reinstall, manual upgrade, package-manager update), P68-05's registered autostart entry still points at the same file path, so the next boot picks up the new binary automatically — no explicit re-registration is needed for a same-path replacement. What P68-05 does not handle is a path change (a different install location), which would leave the old entry pointing at a now-missing file; P68-06's bounded-retry self-deregistration behavior (§4) is what prevents that from looping forever, not a repair — the user (or a future phase) still has to run `rush install` again from the new location to re-register correctly.

Completion requires all seven tasks' (P68-01 through P68-07) VERIFY steps passing on all three platforms this session can reach, plus three full manual runs on real machines: one confirming the entire install experience is exactly one command with a real animated, explanatory progress display (`rush install` or the one-line `curl`/`irm` installer, with MCP, CLI tools, memory, and dashboard all active with nothing else typed and nothing blocking on stdin), one confirming the dashboard survives closing the terminal session and a real device restart with zero manual relaunch, and one confirming `rush uninstall` cleanly removes the autostart entry afterward.

This plan does not authorize implementation. Building P68-01 through P68-07 requires explicit approval to proceed, same as any other plan in this directory.
