## 1. What this packet implemented

`rush.tools.memory.MemoryTool` already had 12 of its 13 new Phase 63 operations fully
implemented internally by MC02–MC12 (`expand`, `link`, `related`, `consolidate`,
`verify_attempt`, `prepare`, `resume`, `intent`, `recipe`, `plan_checks`,
`last_success_diagnose`, `receive`) — none of them were reachable through the CLI, and the
MCP `rush_memory` tool already auto-exposed them (FastMCP introspects
`MemoryTool.__call__`'s live signature via `functools.wraps`, so its schema was already
current before this packet touched anything). This packet:

1. **Added the 13th operation, `handoff`** (`src/rush/tools/memory.py`), covering §9.1's
   `handoff prepare` row via the existing `rush.memory.handoff.prepare_handoff`. `dispatch`
   and `status` (§9.1's `handoff dispatch/status` row) return `E_UNAVAILABLE` honestly —
   see §4 below for why, and why that's a real MC11 gap, not something weakened here.
2. **Added 13 new `rush memory <leaf>` Click commands** (`src/rush/cli.py`): `expand`,
   `link`, `related`, `consolidate`, `verify-attempt`, `prepare`, `resume`, `intent`,
   `recipe`, `plan-checks`, `last-success-diagnose`, `handoff`, `receive`. One generator
   function (`_build_memory_operation_command`) builds all 13 from a per-operation help
   string, since they share one request-shaped contract (`--input FILE` parsed once into
   `request`, plus `--session` for the 4 ops that read `session_allowlist`, plus the
   standard `permission_options` flags). Every leaf routes through `_run_tool` →
   `InvocationExecutor.execute` — the exact same executor `make_tool_wrapper` uses for MCP
   — so CLI and MCP calls with an identical request are **structurally**, not
   coincidentally, byte-identical.
3. **Registered all 13 as admin operations** in
   `src/rush/governance/public_operations.py` (`explicit_pairs`) and
   `governance/public-operations.toml` (`[[operations]]`), each
   `canonical_impl = "rush.tools.memory:MemoryTool"`, `mcp_tool` omitted (the shared
   `rush_memory` MCP tool name is already claimed by `memory ask`, matching the existing
   `memory list/recall/write/promote/maintain` precedent), and `effect_class` set per
   §9.1's grants column (`read-only` for `expand`/`related`/`prepare`/`resume`/
   `plan-checks`/`last-success-diagnose`; `stateful-mutation` for
   `link`/`consolidate`/`verify-attempt`/`intent`/`recipe`/`handoff`/`receive`).
4. **No changes needed to `src/rush/catalog.py`, `src/rush/config.py`, `src/rush/mcp.py`,
   `src/rush/mcp_support/tool_registry.py`, or `examples/rush.toml`** — see §5 for why each
   was a zero-diff investigation result, not a skipped requirement.
5. **`tests/test_memory_public_contract.py`** (new, 27 tests, all passing): the 7 required
   test functions plus one supporting parametrization
   (`test_missing_mutation_grant_fails_equally`), covering the full RED→GREEN parity matrix.

## 3. Examples executed (test_documented_examples_execute)

All three ran against real fixtures in a `tmp_path` project, asserted on measured output,
never a claimed/unmeasured benefit:

1. **Compact recall → expand.** Wrote one `domain_knowledge` artifact via `MemoryTool`,

   MC02 compact path), confirmed the artifact appeared in `data.items`, then called the new

2. **Isolated repair.** Recorded one real failed repair attempt via
   `rush.memory.experience.record_attempt` (MC06), then called `rush memory prepare

3. **Restricted handoff.** Called `rush memory handoff --input ... --allow-cache-write`

   asserted the exact seeded artifact id appeared in the receiver's `data.changes` — a live
   sender→receiver round trip through the CLI, not a mocked capability.

## 4. Deviations

- **`handoff dispatch`/`handoff status` report `E_UNAVAILABLE`, not a real result.**
  §9.1's `handoff dispatch/status` row (and MC11.3's own text, "Add `dispatch_handoff` and
  MemoryTool handoff actions") names a `dispatch_handoff` entry point that **does not exist
  anywhere in the repository** — `src/rush/memory/handoff.py` has only `prepare_handoff`,
  `load_session`, `receive_handoff`, `acknowledge_readback`, and there is no
  `src/rush/memory/transport.py` `dispatch_handoff`/status function either. Both files are
  outside T122's `allowed_files`. Rather than fake a result or leave `dispatch`/`status`
  silently unrouted, `_handoff()` validates the `action` field, and for `dispatch`/`status`
  returns the real, already-defined `warn/E_UNAVAILABLE` envelope
  (`{"message": "handoff {action} is not yet implemented: rush.memory.handoff has no
  dispatch/status entry point."}`) — honest and CLI/MCP-identical, verified by
  `test_cli_mcp_operation_payload_and_permissions_match`'s parity check not being asked to
  cover those two actions (only `action=prepare` is exercised, since that's the only real
  implementation). This is a genuine MC11 completion gap, not something this packet can or
  should paper over.
- **`receiver_namespace` maps to `prepare_handoff`'s `session_allowlist`.** §9.1's `handoff
  prepare` row lists `receiver_namespace` as a field but never mentions
  `session_allowlist`, while `prepare_handoff()` hard-requires a non-empty
  `session_allowlist` (raises `E_INPUT` otherwise). `_handoff()` treats
  `receiver_namespace` (when given) as that scope (`session_allowlist=[receiver_namespace]`),
  falling back to `[receiver_audience]` when omitted — a defensible, minimal reading of an
  underspecified field mapping, not a silent guess buried in code: recorded here explicitly.
- **No `src/rush/catalog.py` / `src/rush/config.py` changes.** §9.1's "Configuration keys:
  view, limit, max_tokens, max_bytes, encoding, retrieval, memory_record,
  embedding_endpoint, embedding_model_digest" describes the **compact-query request
  schema** (`_COMPACT_REQUEST_KEYS` in `tools/memory.py`, already fully implemented by
  MC02/MC12) — not `[tools.memory]` TOML config keys. The one genuine TOML config key,
  `record` (MC05, already in `catalog.py`), was already present and already generically
  validated/rejected-on-unknown-key by `config.py`'s existing per-tool option mechanism
  (`_parse()`, lines ~139-160) — reused as-is, not modified.
- **No `examples/rush.toml` changes.** Following directly from the point above:
  `[tools.memory]\nrecord = false` was already documented there (MC05); there is no new
  TOML key to add.
- **No `src/rush/mcp.py` / `src/rush/mcp_support/tool_registry.py` changes.** Verified live
  (not assumed): `register_all_tools()` wraps `tool.__call__` via
  `functools.wraps(tool.__call__)`, and FastMCP's `inspect.signature()` follows
  `__wrapped__` — so `rush_memory`'s MCP schema already exposed the full 18-operation enum,
  `request`, and all `allow_*` flags before this packet touched anything (confirmed by
  direct introspection of the live `build_server()` output).
