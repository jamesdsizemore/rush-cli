# MC06 — Recall failed repairs by exact conditions

Evidence record for Phase 63 workstream MC06 (`docs/phase-plans/phase-63-memory-capabilities-vibecoder-plan.md` §9, MC06.1-MC06.5). Owned production files: `src/rush/memory/experience.py`, `src/rush/memory/failure_ledger.py`, `src/rush/tools/memory.py`. Owned test file: `tests/test_memory_repairs.py`.

## What MC06 adds

MC01-MC05 are unchanged and untouched by MC06: `store.py`'s versioned `write()`/`search()`/`recall()`, `retrieval.py`'s bounded recall, `relations.py`/`consolidation.py`, and `experience.py`'s existing `record_observation`/`write_observation` (MC05) are only ever *called*, never duplicated or bypassed. `src/rush/memory/failure_ledger.py` needed no code change for MC06 — its three exact-hash callers (`record_failure`, `is_known_failure`, `get_receipt`, used by `continuity/receipts.py`, `continuity/coordination.py` and five test files) are unmodified and still pass; it is listed as an owned file in the plan's §8.1 file map, but no MC06 requirement touches its behavior.

MC06 adds three functions to `src/rush/memory/experience.py`, on top of MC05's existing observation infrastructure:

1. **`record_attempt`** — records one repair-episode attempt (`outcome="failed"|"verified"|"untested"`) under exact §9.0 condition identity, reusing the same `MemoryArtifact`/`TypedArtifactStore.write()` path MC05's `write_observation` already uses. `subject="episodic"` for a verified outcome, `subject="failure"` otherwise (§6.1's "repair episodes use `experience` with `episodic`/`failure`").
2. **`recall_repair_episodes`** — read-only symptom-scoped recall (`TypedArtifactStore.search()` only, exactly the same read primitive `consolidation.py`'s `consolidate_episodes` already uses), bucketed into `failures`/`verified_repairs`/`untested_hypotheses`, with a `match` state (`same`/`changed`/`incomplete`) computed per §9.0 condition identity for failures.
3. **`prepare_memory`** — wraps `recall_repair_episodes`, adds an optional `behavior_ids` filter, and appends `evidence_refs` (the `{id, version}` of every returned episode).

`src/rush/tools/memory.py` wires `prepare` and `resume` as two new `MemoryOperation` values, both dispatching to one `_prepare` handler that calls `prepare_memory` — matching the plan's §9.1 request table row ("`prepare/resume` | task, conditions | behavior_ids=[], query=\"\", budgets above | none"), which gives both operations the identical request shape and zero required grants.

## Condition identity and the three-state match (MC06.2)

§9.0: "Condition identity. Require runtime (implementation and major/minor version), platform (OS and architecture), dependencies (package→resolved-version map), config_digest and source_digest." `_CONDITION_FIELDS = ("runtime", "platform", "dependencies", "config_digest", "source_digest")` in `experience.py`; `_conditions_complete()` checks all five are present.

`_repair_match(candidate_conditions, candidate_patch_hash, query_conditions, query_patch_hash)`:

- **`incomplete`** — either side is missing one of the five fields. Never produces a same-conditions warning (§9.0: "missing fields produce match='incomplete', never same-conditions warning").
- **`same`** — a `query_patch_hash` was given, it equals the candidate's `patch_hash`, and every one of the five condition fields is equal.
- **`changed`** — anything else complete-but-not-identical: a different patch, or the same patch under a changed field (dependency version, config digest, source digest, runtime, or platform). This is the state that "permits retrial and explain[s] mismatch" (§6).

Omitting `query_patch_hash` (as `prepare_memory`'s request shape does — the plan's request table has no `patch_hash` field for `prepare`/`resume`, only `recall_repair_episodes`'s lower-level, directly-tested signature accepts one) can never resolve to `"same"`: recall never asserts an exact repeat for a patch it wasn't asked to compare against.

## Record/recall separation and attribution (MC06.2/MC06.4)

`record_attempt` requires `receipt_ref` for `outcome="failed"` or `outcome="verified"` (raises `ValueError` otherwise) — `receipt_ref` is the only evidence a check actually ran, and `record_attempt` never executes anything to produce one. `outcome="untested"` is the one outcome allowed to omit it: a hypothesis can be recorded before it is ever tried.

A `commit_message` (e.g. a revert or a `"fix:"`-labelled commit) is stored as attribution text only. Per §6 ("Revert messages and `is_fix` commits remain unverified attribution until supported by before/after execution"), the label is never inspected to auto-upgrade `outcome` — `test_revert_and_fix_label_do_not_prove_cause` asserts (a) attempting `outcome="verified"` with `receipt_ref=None` and a `"fix:"`-labelled `commit_message` raises `ValueError` (the label alone cannot substitute for a receipt), and (b) an `outcome="untested"` attempt with a `"revert ..."` `commit_message` lands only in `untested_hypotheses`, never in `verified_repairs` or `failures`.

`recall_repair_episodes` buckets strictly by the stored `outcome` field, never by text content or label — `test_failed_and_successful_conditions_remain_distinct` records one failed and one verified episode for the same symptom and conditions, and asserts the two ID sets (`failures` vs `verified_repairs`) are disjoint.

## `prepare`/`resume`: read-only, never a subprocess, never a prohibition (MC06.3/MC06.4)

`MemoryTool._prepare` (`tools/memory.py`) validates `{task: str, conditions: dict, behavior_ids?: list[str], query?: str}`, then calls `prepare_memory(project_root=root, symptom=query or task, conditions=conditions, behavior_ids=behavior_ids, session_allowlist=session_allowlist)`. No `ExecutionPermissions` check is applied (matching the plan's request table: prepare/resume require no grants), and the handler never imports or calls anything from `subprocess`, `rush.patch.*`, or `rush.invocation.*` — the only I/O is `TypedArtifactStore.search()` (SQLite reads).

`test_prepare_exposes_untested_hypothesis_without_executing` monkeypatches `subprocess.run` and `subprocess.Popen` to raise `AssertionError` if called at all, then drives both `operation="prepare"` and `operation="resume"` through the real `MemoryTool.run()` (not a mock), and separately calls `prepare_memory` directly — all three calls return normally with the previously-recorded untested hypothesis present in `data["untested_hypotheses"]` and its `{id, version}` present in `data["evidence_refs"]`. The response also carries no `"denied"`/`"prohibited"` field: `prepare`/`resume` only ever surface evidence, they never veto a patch a caller might choose to try.

## Deviations

- **`prepare`/`resume` request schema omits the plan's listed budget fields** (`max_tokens`/`max_bytes`/`encoding`). The plan's §9.1 table lists "budgets above" as optional/default fields for `prepare`/`resume`, but no required test exercises truncation, and MC06's episode volume (bounded by however many repair episodes a project actually has for one symptom) does not need MC02-scale pagination. Accepting these fields without enforcing them would be a faked capability; they are left out of `_PREPARE_REQUEST_KEYS` rather than silently ignored. Add real budget enforcement (reusing `retrieval.py`'s existing serialization budget code) if/when a task needs it.
- **`failure_ledger.py` received no edits.** It is an owned file per the plan's §8.1 file map, but no MC06 requirement or named test needed a change to it; its exact-hash callers were re-verified unchanged (full suite green).
- `record_attempt`/`recall_repair_episodes`/`prepare_memory` all take `project_root`/`session_allowlist` etc. as keyword-only, matching `write_observation`'s existing keyword-only convention in the same file.
