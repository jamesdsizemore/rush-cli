## 3. Contract clarifications (supersede named Phase 66 §3 clauses only)

These resolve Phase 66 §0's rows 21-24 (internal contract ambiguities and one ordering defect in the contract's own wording), plus one round-7 addition (below) resolving a real ownership-model gap §3.9's original wording never anticipated. Nothing else in Phase 66 §3 changes.

**Supersedes Phase 66 §3.2/§3.7 Bearer-auth clause (row 21).** Bearer authentication is bootstrap-exchange-only: a one-use credential, valid for first exchange or 5 minutes, after which only the cookie session or a freshly issued `--reconnect` bootstrap authenticates. There is no separate long-lived programmatic credential. A programmatic client that needs a new session calls `rush dashboard --reconnect --json` for a fresh one-use bootstrap URL, the same mechanism a human reconnect uses. This matches already-shipped behavior (`server.py:1535`) rather than adding a new credential surface.

**Supersedes Phase 66 §3.7 cross-server-isolation claim (row 22).** "A server's auth/state cannot affect another server" means cooperating Rush-launched servers never collide (distinct random cookie names, distinct auth/session state per `DashboardContext`). It does not claim isolation from an untrusted, non-Rush, same-host service on another port — host-only `Path=/` cookies are not port-scoped, and no cookie mechanism makes them so. This is a stated, accepted threat-model boundary, not a defect to code around.

**Supersedes Phase 66 §3.1/§3.6 memory-write "scope" clause (row 23).** `scope` in the browser/TUI memory contract means an explicit **ownership** field distinct from the existing `subject` field on `MemoryArtifact` (`src/rush/memory/store.py:71-87`, read directly this session to carry no ownership field today — `subject` is a `MemorySubject` enum value such as `domain_knowledge`, not an owner). Every memory write from the dashboard/TUI must carry `owner_scope: {kind: "user"|"project"|"session"|"agent", id: str}` in addition to `subject`; P69-07.2 adds this as a real, migrated `MemoryArtifact` field, not an HTTP-layer-only tag.

**Supersedes Phase 66 §3.4 animation-cancellation ordering (row 24).** "Cancel prior animations, retain current computed transform as next animation's start" is ordered wrong as written — cancelling first removes the animated effect before its visible intermediate position can be read back. The corrected order, which P69-05.2 implements: capture the live visual transform first (read the actual current on-screen position, not the target/final value), then call `cancelActiveAnimations()`, then start the new animation from the captured value. This clause is the resolution P69-05 implements; P69-05 cites this clause directly rather than restating it.

**Supersedes Phase 66 §3.9 Detach-on-locally-owned-run clause (round-7 addition, added by P69-06).** §3.9's unchanged text ("TUI quit with running work offers Detach (default), Cancel run and stay, Return") does not distinguish a dashboard-owned run from a locally-owned one, because Phase 66 never had the dashboard-vs-local ownership split P69-06 introduces. Detach requested against a run with a live dashboard server behaves as real background continuation, matching §3.9's original intent exactly (the TUI stops observing, the work keeps running in the already-alive dashboard process). Detach requested against a run with no live dashboard server (a bare local daemon thread) behaves as an immediate Cancel-with-saved-partial-result, since no mechanism this phase can build keeps a standalone CLI process's work alive after that process exits — this is the one case where "Detach" cannot mean what §3.9 originally intended, named and resolved here rather than silently substituted. Cancel run and stay and Return are unaffected by this clause and behave exactly as §3.9 specifies in both ownership cases: Cancel run and stay cancels the work without the TUI process exiting; Return dismisses the prompt with no cancellation and no exit. P69-06 implements this resolution; P69-06 cites this clause directly rather than restating it.

   **f. Per-operation-kind recovery receipts.** A preallocated ID only answers the recovery question for creation. Edit/archive/delete act on an artifact that already existed — a lookup by ID can't tell you whether *this* request's edit applied (only that the artifact exists). A before/after version comparison can't identify which request produced a version either (an unrelated request can advance the same artifact after the original owner crashes), and a tombstone written before delete proves intent, not completion.

      The receipt must be written *inside the same transaction as the effect itself*, using the store's real transaction boundary (the same pattern `_prepare_write`/`delete_batch` already use): add a `mutation_receipts` table that `edit()`/`archive()`/`delete()` each write to atomically alongside their own row mutation, containing the ledger's preallocated operation id and the resulting row state. Recovery reads this receipt by operation id — exists means committed, regardless of what any other request did to the artifact afterward; absent means never committed, resume as never-attempted. For handoff (multiple separately-persisted effects — session creation, then memory artifact), one receipt per distinct effect, each with its own preallocated ID, committed atomically with that specific effect's own transaction.

      **Promotion is two separately-committed effects, not one.** `MemoryTool._run_promote()` commits `store.write()` (creating the candidate artifact) before separately calling `store.promote()` — a receipt keyed only to artifact-creation would report promotion done when it crashed between the two calls.    **g. `_prepare_write()` atomicity.** `_prepare_write()` runs its conflict lookup and conflict-delete *before* `write()`/`write_pass()` opens the new artifact's own insertion transaction — a process death between the delete committing and the insert committing permanently removes the original artifact with nothing replacing it, and (f)'s receipt contract would see no creation receipt and wrongly conclude "never committed" while the destructive delete already happened.    **h. Owner-liveness lock and scan-exclusion lock (two separate locks, not one).** Recovery needs to know who owns an in-flight operation, or two server instances can corrupt each other's recovery. The reservation/status schema carries the owning server's identity (`server_id`/`start_nonce`, `DashboardContext.__init__`) and a liveness signal; a server starting up (or a recovery worker) claims a `pending` row only via an atomic claim (CAS on `claimed_by`/`claimed_at`), and marks an operation interrupted only after positively establishing the recorded owner process is gone — never via an HTTP health check (unreachable ≠ dead: the process could be alive but slow or network-partitioned).

      A single per-project lock held by every server for its whole lifetime directly contradicts `create_dashboard_server`'s own supported-concurrency guarantee (two servers legitimately running against the same project). Split into two genuinely separate locks:

      - **Owner-liveness lock** — keyed by an immutable per-executor-instance identity (`server_id`/`start_nonce` for a dashboard server; an equivalent per-invocation instance id for a standalone TUI process or local `CHECK_SUITE` job — never keyed by project), acquired once at startup, held for that instance's entire process lifetime (`.rush/owners/<owner_instance_id>.lock`, `fcntl.flock(fd, LOCK_EX | LOCK_NB)` on POSIX; identify the real Windows-equivalent primitive during RED — a named mutex, not another O_EXCL file). No heartbeat/renewal needed — the kernel releases the lock the moment the holding process exits, including a crash. Every executor that can own recoverable work — dashboard servers, standalone TUI processes, local `CHECK_SUITE` jobs — must acquire its own owner-liveness lock before reserving any work under this contract.
      - **Scan-exclusion lock** — still per-project, replacing `_run_lock()`'s current `O_CREAT|O_EXCL`-plus-age-based-staleness scheme (`project_run.py:174-207`), which unlinks a lock file purely on elapsed time with no owner-liveness check, letting a second process steal a still-live scan's lock and letting the original owner's cleanup then unlink the new owner's lock instead of its own. Held only during an actual scan's execution — acquired when a scan starts, released when it finishes — so a surviving server can run scan after scan without restarting. Keep the existing 5s acquisition-attempt timeout (`ScanBusyError`) for a waiting caller's own patience, decoupled from the lock's staleness.

      Recovery reads a `pending`/`recovery_required` row's recorded owner-instance id and attempts a non-blocking acquisition of that specific owner's lock file: success means that owner's process genuinely exited (every row tied to it can be reconciled); failure means that owner is still alive, regardless of how slow it's been, and says nothing about any other owner or the project as a whole. Retain PID as diagnostic-only metadata, never part of the recovery predicate.

      **Execution-gate mechanism.** Persisting the `.procs` record right after `Popen()` narrows the unfenced window but doesn't close it — the child can begin real work before the write lands. A post-launch `SIGSTOP` doesn't establish the guarantee either (`Popen()` only waits for fork+exec to report success, not for the executed program to reach any instruction), and Windows has no usable `CREATE_SUSPENDED` path through `subprocess`.

      Use a bootstrap gate the real engine binary cannot get past before it starts, identical shape on both platforms: spawn a tiny inherited-pipe-blocking wrapper in place of the real engine command, which launches the real command only after being explicitly released, and never launches it at all if the parent dies first.

      *POSIX:* create an anonymous pipe (`os.pipe()`); spawn `["/bin/sh", "-c", 'read -r _ <&"$RUSH_GATE_FD" && exec "$@"', "sh", *real_argv]`, with the pipe's read end passed via both `pass_fds=(read_fd,)` and `env={**current_env, "RUSH_GATE_FD": str(read_fd)}`. The owner then, in order: (1) persists `(owner_instance_id, run_id, pgid)` to `.rush/owners/<owner_instance_id>.procs` and `fsync`s it — `pgid` is the gate shell's own pid, stable across its later `exec`; (2) writes exactly `b"\n"` to the pipe's write end and closes both ends (including its own copy of the read end). Only once the shell's blocked `read` returns does `exec "$@"` replace it with the real binary — it never starts before that point. If the owner dies before step (2), its copy of the write end closes with it; the shell's `read` returns EOF, `&&` short-circuits, and the shell exits without ever `exec`ing — airtight, not a narrowed race.

      *Windows:* identical pipe-plus-EOF mechanism (`CreateNamedPipe`/`AnonymousPipeServerStream`+`AnonymousPipeClientStream`, exact API decided during RED) — not a separate event-object design (an event-based design is unsound: closing the owner's handle doesn't signal the wrapper's separate handle, and `WAIT_ABANDONED` is a mutex semantic, not an event one).

      **Cleanup discipline.** `Popen()`'s internals fork the child before the constructor returns, so an interruption between fork and return can leave a live, unrecorded gate process. Wrap pipe allocation and the gate `Popen()` call in `try`/`finally`, running on every exit. Guard each cleanup action independently (track every fd/handle opened; close each in its own `try`/`except`, collecting rather than propagating failures; attempt the best-effort reap in its own independent `try`/`except`, only if a process object exists) — a fault-injected close failure must not replace or skip the original propagating exception. A record-write/`fsync` failure is itself an original exception (not a "no exception" case) — whichever exception is in flight when cleanup begins (gate-spawn failure or record-write failure) is what propagates; a cleanup failure encountered while handling it attaches as chained/suppressed context, never substitutes. A cleanup failure only becomes the propagating error on an ordinary successful exit with nothing else in flight.

      **Termination.** Recovery (a different process, no access to the original `Popen` handle) and Detach's own force-exit read the recorded `pgid` directly: send SIGTERM to the group, poll every member for actual exit (not just the leader) with a bounded deadline (5s, matching Detach's timeout), then SIGKILL any survivor, then a second bounded confirmation poll. Only remove the `.procs` record and let recovery reconcile the row once that confirmation poll positively observes every group member gone. If a survivor remains when the deadline expires, do not clear the record and do not let recovery reconcile — mark an explicit `termination_unconfirmed` flag alongside `recovery_required` blocking new conflicting work, leaving the row for the next recovery attempt to retry against the same pgid. Identify the real Windows-equivalent group-termination primitive during RED (`CREATE_NEW_PROCESS_GROUP` plus `GenerateConsoleCtrlEvent`/`TerminateProcess` on the recorded PID tree, not `os.killpg`).

   **k.    **f.       Admission: attempt `INSERT` keyed by `project_id` alone.       The admission boundary is transaction **commit**, not `INSERT` returning without error (SQLite: a conflicting `INSERT`'s surrounding transaction is still live until it commits). The winner's `INSERT` transaction must actually commit before its operation's thread is launched or its 202 is sent — never launch speculative work before the admitting transaction has durably committed. The loser's attachment-record write happens *inside the same transaction* as its own conflict-triggered read — no split-transaction alternative (a read that commits separately from the attachment write reopens the race where the winner terminalizes and frees its slot in between).    **g. Terminal-slot release and worker supervision.** The admission row and the attachment record are independent lifecycles: the admission row is ephemeral (exists only while a project has an active job; deleted the moment that job reaches terminal state) and the attachment record is retained per its own normal TTL, unaffected by the admission row being freed.

      **Terminal-slot release:** the moment an operation reaches a genuine terminal state (success, failure, or reconciled interrupted outcome), atomically delete its admission row in the *same* transaction that records its terminal status transition (`record_status_transition()`, P69-01.2). This terminalize-and-release action is one idempotent transaction, callable from every real exit path, safe to retry — never a bare, unconditional `finally: <release>` (see the crash-durability note below).

      **In-process worker supervision:** every dispatcher's background closure (`_run()` in `_dispatch_scan_resume`/`_dispatch_rescan`/etc.) currently does `with suppress(Exception): <call>` (`server.py`, e.g. `:480-482`), silently swallowing failure and leaving the admission row occupied forever. Change every such closure to call the idempotent terminalize-and-release transaction on any exception, from a `finally` block that does *nothing else*: a bare `finally: <release>` is unsound because `SystemExit` bypasses `except Exception` but still enters `finally`, and the terminal-status write itself can fail and still reach `finally` — releasing the row in either case leaves a reservation that never reached a real terminal state with no admission protection at all. If the terminalize-and-release transaction itself fails, the admission row is **not** independently deleted; it stays as-is, naming this operation's `owner_instance_id`, left for recovery's recurring sweep (below) to retry — never a fallback "just delete the row anyway" path.

      **Thread-launch failures happen outside any worker closure.** The real `start_or_attach()` (`state.py:225`) calls `thread.start()` internally, not `_run()` — a launch failure (resource exhaustion) raises back to the *dispatcher*, after the admission row already committed, with no worker closure ever running to catch it. The dispatcher itself wraps its own `start_or_attach()`/`thread.start()` call and, on launch failure, calls the same idempotent terminalize-and-release transaction directly — a third call site for a third real failure mode, not a new mechanism.

      **Durable pending-outcome handoff, to survive a transient terminalization failure.** Recovery alone clears a dead server's row (never a live-request takeover). But if the terminalization transaction fails transiently while the owner is genuinely still alive, nothing above makes that failure durably visible for retry. Fix: immediately before attempting the terminalize-and-release transaction, the worker/dispatcher hands the real outcome (operation id + terminal status/result, nothing else) to a small, in-memory, **server-process-owned retry queue** — before attempting the durable pending-outcome write at all. That queue, not the exiting worker, owns retrying the pending-outcome write and then the terminalize-and-release transaction for as long as the server process stays alive. This applies uniformly to normal completion, an exceptional exit, and a launch failure. The only way an outcome is truly lost is the server *process* itself dying before the queue durably registers anything even once — which is exactly the case P69-01.2's pre-existing receipt-based dead-owner reconciliation already handles (process death releases the owner-liveness lock; reconciliation determines the real outcome from the receipt). There is no further level to recurse into.

      Recovery's sweep gains a third, distinct check alongside the existing dead-owner one: an admission row whose owner is *alive* but which has a durably-registered pending-outcome not yet reflected in the ledger is retried using that recorded outcome — never by re-executing the operation's work, only by retrying the bookkeeping write.

   **h. Recovery.** Recovery — never a live-request takeover — is the only path that clears a dead server's row, and is also the retry mechanism for a same-process terminalization that failed on its own. When P69-01.2's recovery sweep finds an admission row whose `owner_instance_id` is established dead (per the existing kernel-lock check), it reconciles the operation using its recorded identity/arguments exactly as it does for every other row kind, and writes the real terminal outcome, which atomically clears the admission row as a side effect. A live request conflicting with a dead-owner's (or failed-terminalization's) row receives the identical structured busy/conflict response as if the owner were live — it never attempts takeover itself; it retries later, by which point the next recovery sweep has either cleared the row or not yet run.    **i. Retention and pruning.** The existing TTL-pruning contract (never prune a non-terminal `pending` row, only prune once genuinely terminal) has no defined interaction with attachments. An attachment record's terminality is *derived* from its executing operation's terminality (nothing ever writes a status transition directly to it) — it is pruned in the same pass as its executing operation's now-terminal-and-expired row, never earlier and never on its own timer.

      Define one transactional deletion unit: before deleting anything, discover the **complete transitive attachment set** pointing at the terminal, expiring row — every row whose attachment chain resolves to this target, however many hops away (a chain `A → B → C`: discovering only direct references to `C` finds `B` but misses `A`) — then delete the target's own row, every discovered attachment record, and every discovered row's own reservation entry together, in one transaction.

      Open the pruning transaction with `BEGIN IMMEDIATE` (acquiring the write lock before discovery runs) — a plain deferred `BEGIN` does not serialize discovery-through-deletion against a concurrent attachment-creation write in WAL mode. Attachment creation revalidates the target's existence *inside its own transaction* at insert time (reusing the same existence-check-inside-the-transaction pattern the admission table's unique-constraint `INSERT` already relies on). On any contention/busy signal during pruning, roll back and restart the *entire* transaction (re-discover, re-validate, re-delete) — never retry only the `DELETE` against previously-discovered, now-potentially-stale rows. Bound the retry loop with a total deadline and backoff (exact values decided during RED, matching this repo's existing bounded-retry pattern if one exists). If the deadline is exhausted, leave the rows exactly as they were and defer to the next scheduled sweep — an availability concern, never a correctness one, since the rollback-on-contention discipline guarantees nothing partial survives.

      Discovering the reverse set (who points *at* this row) needs an explicit mechanism — a reverse index keyed by executing-operation-id is worth having at scale, but a full-table scan/snapshot traversal over attachment records, run inside the same deletion transaction, is the correctness-sufficient baseline; add the index only if profiling shows it's needed.

      The admission-table redesign in (f) removes the "decided but never durably written" scenario at its root: because the admission decision and its persistence are the same atomic `INSERT`, there is no state where a request has "decided to attach" without that decision already being on disk.
