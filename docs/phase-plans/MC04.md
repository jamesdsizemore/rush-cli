# MC04 — Remove duplicate retrieval work and count actual costs

Evidence record for Phase 63 workstream MC04 (`docs/phase-plans/phase-63-memory-capabilities-vibecoder-plan.md` §9, MC04.1-MC04.5). Owned production files: `src/rush/token_economy/memory_cache_gate.py`, `src/rush/tools/review.py`, `src/rush/continuity/context.py`, `src/rush/token_economy/telemetry.py`, `src/rush/memory/retrieval.py`. Owned test file: `tests/test_memory_efficiency.py`.

## The duplicate work being removed

Before MC04, `memory_cache_gate.check_memory_before_pack()` and `review.py`'s `_recall_memory_citations()` each ran their own `store.search()`-then-`store.recall()` pair: a precheck `search()` call, followed by `recall()`, which internally calls `search()` again — two identical FTS queries per logical lookup. `recall()`'s per-row loop then re-read and re-hashed (`MerkleInvalidator.hash_content`) and re-ran a `git show` subprocess (`ApiDiffer.diff_symbol`) for *every matching row*, even when multiple rows shared the exact same backing source file (e.g. two `DERIVED` cache-fill rows for the same `context_path`, or two failure-memory citations naming the same file).

MC04 replaces both call sites with one shared `defended_recall()` (new, in `retrieval.py`): a single `store.search_candidates()` query (MC02's own already-bounded/ranked path — never a second raw FTS query, never a hand-rolled duplicate of its filtering logic) validated with `store.recall()`'s exact signature/Trojan-source/staleness checks, routed through a request-scoped `SourceValidationMemo` so N candidates sharing one file are hashed/API-diffed once, not N times. `store.py` itself (MC01/MC02/MC03's `search()`/`recall()`/`search_candidates()`) was not touched — MC04 is a consumer-side fix only.

## Measured counts (not a latency claim)

Measured directly against the real `TypedArtifactStore`/`MerkleInvalidator`/`ApiDiffer` call sites (`unittest.mock.patch.object(..., autospec=True, side_effect=<original>)`, so the real implementation still runs — only the call count is observed), for the two scenarios `test_cache_and_review_do_one_defended_search` exercises. A lower call count is real reduced work (fewer SQL executions, fewer file reads, fewer subprocess spawns); it is not by itself a wall-clock latency guarantee, since actual latency also depends on OS file-cache state, SQLite's own query planning, and git's cold/warm state.

**Cache-gate lookup, 2 rows sharing one source file** (`check_memory_before_pack("module.py", "hello", ...)` against two `DERIVED` rows both keyed to `module.py::hello`):

| | SQL queries | source file reads/hashes | `git show` (API-diff) calls |
|---|---|---|---|
| Before (`search()` + `recall()`) | 2 | 2 | 2 |
| After (`defended_recall()`) | 1 | 1 | 1 |

**Review citation path, 1 target × 2 subjects, 2 matching rows sharing one source file** (`_recall_memory_citations()` over one target, subjects `failure` + `architectural_decision`, with two `failure` rows both keyed to `mod.py::thing` and zero `architectural_decision` matches):

| | SQL queries | source file reads/hashes | `git show` (API-diff) calls |
|---|---|---|---|
| Before (`search()` + `recall()`, per subject) | 3 (2 for the matching subject, 1 precheck-only for the empty one) | 2 | 2 |
| After (`defended_recall()`, per subject, shared memo) | 2 (1 per subject) | 1 | 1 |

Both scenarios are asserted directly (not just narrated) in `test_cache_and_review_do_one_defended_search` and `test_shared_source_validated_once_per_request` via the same `autospec` call-count technique shown above.

## Complete cache identity (MC04.3)

The on-disk `cache_key` field stays the plain `f"{context_path}:{target_symbol}"` string — an existing, pinned contract other call sites (`tests/test_phase62_cache_gate.py::test_cache_miss_write_back_uses_derived_trust_tier_and_exact_key`) match against literally, so it was never safe to replace with a hash. Instead, `write_cache_fill()` now stores a nested `cache_identity` dict alongside it: `namespace` (`str(store.project_root)`), `audience` (the fixed `context_pack` source tag), `engine_revision` (a bumped-on-algorithm-change constant), and, when the caller supplies them, `token_budget`, `encoding` (tokenizer), and `view` (`as_v1`). `check_memory_before_pack()` accepts the same optional `token_budget`/`encoding` and only rejects a hit when the request supplies a value **and** the stored row has a value for that same dimension and they differ — a legacy/seeded row with no `cache_identity` at all (e.g. `tests/test_phase62_cache_gate.py`'s hand-seeded rows) still hits exactly as before. `context.py::pack_context()` threads its own `token_budget`/`as_v1` straight through since it already has them; no new parameters were added to `pack_context()`'s own signature.

"Scope" (a different `MemorySubject`) was already structurally isolated by `search_candidates()`'s `WHERE ma.subject = ?` — no new code needed, only a test (`test_cache_key_changes_with_budget_scope_and_tokenizer`) exercising it. "Config" is not represented: `pack_context()` has no config object flowing through this call path today, and adding one to satisfy the identity list literally would have been a fabricated dimension with no real caller ever varying it — omitted rather than invented (recorded as a deviation, not silently dropped).

## Telemetry: real, deduplicated, opt-in-gated (MC04.3/MC04.4)

`TelemetryStore` gained a second table, `memory_events(request_id, event_id, kind, tokens, timestamp, PRIMARY KEY(request_id, event_id))`, and `record_memory_event(kind, tokens, *, request_id, event_id, opt_in=False, cache_write=False)` / `get_memory_event_total(kind=None)`. `kind` is one of `retrieval`/`expansion`/`packing`/`handoff`/`embedding` (`embedding` has no wired producer anywhere in this codebase — included as a valid kind for when one exists, not fabricated as an active call site). Persistence requires `opt_in` or `cache_write`; the `PRIMARY KEY` makes a replayed `(request_id, event_id)` pair an `INSERT OR IGNORE` no-op, so re-running the same request never inflates the total (`test_expansion_and_handoff_costs_are_not_double_counted`: two distinct `expansion` events of 10 and 20 tokens sum to 30 via `get_memory_event_total(kind="expansion")`; replaying the first event's ID with a different token count leaves the total at 30).

Real call sites wired: `context.py::pack_context()` records a `packing` event (tokens = `estimated`) only on a genuine cache **miss** with `granted.cache_write` — a cache hit re-delivers already-paid-for content and is never counted, and the existing CCR-overflow/budget-denied envelope paths (pinned by `tests/test_phase44_context_pack_cache.py::test_continuity_overflow_does_not_claim_or_record_unmeasured_token_savings`, which asserts `events_count == 0` and a `"not_measured"` telemetry state) are untouched — no event fires there. `context.py::retrieve_context()` records a `handoff` event (real tiktoken-counted tokens) only on an actual content recovery with `granted.cache_write`. `retrieval.py`'s `recall_page()`/`expand_artifact()` gained optional `telemetry`/`request_id`/`event_id`/`opt_in`/`cache_write` keyword parameters (all default `None`/`False`) that record `retrieval`/`expansion` events on their real successful-page/successful-expansion paths only — omitted (the default, and the only way `rush.tools.memory.MemoryTool`, outside MC04's owned files, calls them today), these are a no-op, so existing callers see zero behavior change.

`check_memory_before_pack()` and `_recall_memory_citations()` (both pure reads) never import or call `TelemetryStore` at all — `test_read_only_recall_never_persists_telemetry` asserts no `.rush/telemetry` directory exists after either runs standalone, and that a subsequent cache **hit** (after a prior miss already created and populated it) leaves `get_memory_event_total()` unchanged.

## Deviations

- "Config" omitted from cache identity (see above) — no real config object exists at this call site to capture honestly.
- `view` (`as_v1`) is recorded in `cache_identity` but not compared on lookup (no test requires a view-mismatch miss, and `pack_context()`'s packed content doesn't actually vary by `as_v1` today — only the output envelope shape does, downstream of the cache).
