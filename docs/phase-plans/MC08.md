# MC08 — Resolve recipes against current source and dependencies

Evidence record for Phase 63 workstream MC08 (`docs/phase-plans/phase-63-memory-capabilities-vibecoder-plan.md` §9, MC08.1-MC08.5). Owned production files: new `src/rush/memory/recipes.py`, `src/rush/tools/memory.py`. Owned test file: `tests/test_memory_recipes.py`.

## What MC08 adds

MC01-MC07 are unchanged and untouched: `store.py`'s `write()`/`get_current()`/`update_content()`, `trust.py`'s `default_entry_tier`, and `verification.py`'s existing `verify_attempt`/`parse_patch_contract` (MC05) are only ever *called* by MC08's new code, never duplicated or bypassed.

`src/rush/memory/recipes.py` (new) adds:

1. **`resolve_symbol_source(project_root, symbol_ref)`** — reads `symbol_ref` (`{"path": relative-file, "symbol": dotted-name}`) straight off disk every call via `ast.parse` + `ast.get_source_segment`, never a cached/graph snapshot, and returns `(exact_source_text, sha256_hex)` or `None` if the path/symbol no longer resolves. `ponytail`: a single-file AST lookup, not a cross-file `rush.codegraph` resolver — MC08's owned writes are `recipes.py`/`tools/memory.py` only, and no required test needed cross-file/re-export resolution.
2. **`record_recipe`** — creates a new recipe (`recipe_id` used directly as the `MemoryArtifact.id`, `family="skill"`/`subject="skill_pattern"` per plan §6.1) or re-records an existing one via `TypedArtifactStore.update_content()`'s compare-and-swap path (mirrors MC07 `intent.record_intent`). `helper_ref` must resolve on disk at record time; its exact current source and hash become the recipe's baseline. Prior `outcomes` are always carried forward on re-record, never dropped.
3. **`resolve_recipe`** — read-only: re-resolves `helper_ref` on disk right now and compares its hash against the recorded baseline; a mismatch (or an unresolvable helper) makes the recipe `usable=False` with a named `reason`, before any other predicate is even checked. Only if the helper still matches does it check `required_symbols` (each must still resolve), `required_dependencies` (each declared name/version must equal the caller-supplied `current_dependencies`), and `required_config_digest` (must equal caller-supplied `current_config_digest`) — an empty list/dict/`None` on any of these imposes no predicate. `checks`/`exceptions` are always returned, identical, regardless of `usable`.
4. **`record_recipe_outcome`** — appends one outcome to `recipe_id`'s `outcomes` list, gated on `recipe_version` (compare-and-swap) and a real, resolvable `verifier_receipt_ref` pointing at a `sandbox_verification` observation written by MC05's `verify_attempt`. There is no `passed=` parameter anywhere on this function — `passed` is derived only from resolving the receipt's own `outcome` field, so a bare `passed=True` claim is a `TypeError` (unexpected keyword), not a rejected value. Never touches `required_symbols`/`required_dependencies`/`required_config_digest`/`checks`/`exceptions`, and `update_content()` never touches `trust_tier` — one passing outcome cannot promote the recipe toward `STATED` or widen what makes it applicable.

`src/rush/tools/memory.py` wires a new `"recipe"` `MemoryOperation` with a single `_recipe` handler dispatching on `request["action"]` in `{"record", "resolve", "outcome"}`: `record`/`outcome` call `record_recipe`/`record_recipe_outcome` (both require `cache_write`, same gate as `write`/`promote`/`intent`); `resolve` calls `resolve_recipe` and requires no permission grant — matching the plan's §9.1 request table row ("`recipe` | action, recipe_id | record fields from MC08; resolve conditions; outcome recipe_version/patch_hash/receipt_ref | cache_write for record/outcome; none for resolve").

## Why resolution reads disk on every call, never a cached snapshot (MC08.2/MC08.4)

The whole point of a "current project implementation" recipe is that staleness is caught the moment the underlying code changes — not at some later re-sync step. `resolve_symbol_source` therefore never memoizes: every `resolve_recipe` call re-reads `helper_ref`'s file and re-parses it with `ast`, so a same-session edit to the helper (or to a `required_symbols` dependency) is visible on the very next call. This is also why `record_recipe`'s re-record path re-resolves `helper_ref` (defaulted from the prior record when omitted) rather than blindly copying forward the old `helper_source`/`helper_source_hash` — a deliberate re-record after an intentional adaptation should re-baseline against what's actually on disk now, not silently keep asserting the old baseline.

## The authority rule, structurally enforced (MC08.3/MC08.4)

`record_recipe_outcome` has no `passed` parameter. The only way its content's `outcomes` list ever gets a `"passed": True` entry is through `_verifier_outcome(receipt.content)`, which requires the resolved artifact to (a) exist at exactly the given `version` (a stale/superseded ref is rejected outright, `E_INPUT`), and (b) carry `evidence_kind == "sandbox_verification"` with a recognized `outcome` (`"completed"|"failed"|"unavailable"`, `rush.patch.contracts.PatchOutcome`'s own vocabulary) — the same evidence kind and vocabulary `rush.memory.verification.verify_attempt` writes via `write_observation`, never a second/parallel verification path. `test_adaptation_pass_does_not_prove_universal_recipe` asserts both structural facts directly: calling `record_recipe_outcome(..., passed=True)` raises `TypeError` (no such keyword exists to accept), and calling it with `verifier_receipt_ref={"id": "does-not-exist", "version": 1}` returns `"E_INPUT"` — a bare claim with no real receipt is rejected before any patch is even considered.

The same test then runs one **real** adaptation through the existing MC05 sandbox route (`verify_attempt` → `PatchSandboxManager` → `PatchApplier` → `PatchVerifier`, applying a real unified diff generated by `rush.patch_generator.generate_unified_diff` in an isolated git worktree, executing `python check_invoice.py` there), records that real receipt's outcome, and then proves the pass does **not** universalize the recipe: `store.get_current("invoice-csv").trust_tier` is still `"EXTERNAL_WRITE"` (never `"STATED"`), `required_dependencies`/`checks`/`exceptions` are byte-identical to what was recorded before the outcome, and `resolve_recipe` under a *different* `current_dependencies` (`{"parser": "2.0"}` against a declared `{"parser": "1.0"}`) still returns `usable=False` with the same real `"dependency mismatch"` reason as before any outcome existed. A second `record_recipe_outcome` call reusing the now-stale `recipe_version` is refused with `"E_VERSION"`, never silently applied against whatever version happens to be current.

## Rejection reasons produced (verbatim, from `resolve_recipe`)

- Stale helper source (`test_api_change_rejects_stale_recipe`): `"helper source changed since recorded (recorded_hash=..., current_hash=...)."`
- Dependency version drift (`test_dependency_or_applicability_mismatch_explained`, `test_adaptation_pass_does_not_prove_universal_recipe`): `"dependency mismatch: 'parser' expected '1.0', got '2.0'."`
- Missing required symbol (`test_dependency_or_applicability_mismatch_explained`): `"missing required symbol: {'path': 'other_helper.py', 'symbol': 'helper_two'}."`

Each names its own predicate distinctly (`"dependency mismatch"` vs. `"missing required symbol"` vs. `"helper source changed"`) — `test_dependency_or_applicability_mismatch_explained` asserts the two applicability reasons are literally unequal strings, not a single generic "mismatch" message.

## Deviations

- **`resolve_symbol_source` is a single-file `ast`-based lookup, not a call into `rush.codegraph`.** The plan's MC08.2 language ("resolve current code through graph/context pack") is satisfied by resolving current code straight off disk on every call — the invariant that matters (never a cached/frozen snapshot) holds either way, and no required test needed cross-file/re-export symbol resolution. Flagged here rather than silently narrowed; a future recipe needing a symbol reachable only via `rush.codegraph`'s call-graph (an inherited method, a re-export) would need this upgraded.
- **`required_dependencies` and `required_config_digest` are caller-declared at `resolve_recipe` time (`current_dependencies`/`current_config_digest` parameters), not read from an installed-package manifest or the real project config.** This mirrors the existing MC06 `record_attempt`/`compare_last_success` "conditions are caller-declared, never environment-inspected" precedent already established elsewhere in this module family — `recipes.py` does not add a second, inconsistent convention for the same kind of fact.

**Amendment (T113 review, board `phases-64-63-65-66`):** the codegraph-bypass above is a deliberate choice, not an oversight -- `CodeGraphStore` is an offline-populated index with no evidence of live rebuild per call, so routing staleness detection through it would risk reintroducing the exact stale-snapshot problem MC08 exists to catch; `ContextPacker`'s skeletonized output is also not demonstrated to preserve byte-exact source for hash comparison. The live-`ast`-read approach was chosen specifically because it is provably never stale within a session, which neither existing tool guarantees today.
