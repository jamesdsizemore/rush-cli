## 1. Goal and scope

A beginner runs one copyable command appropriate to their shell. Rush installs once for the operating-system user account, is available from any directory and manages many repositories without reinstalling Rush inside each project. This is global availability for that account, not an administrator installation shared across every OS account. No source checkout, Python, uv or manual agent JSON editing is required. Installation discovers coding agents, configures supported connections, initializes user-scoped memory and checks readiness independently of whether any project exists.

First launch offers four working choices: select a registered project, add an existing folder, create a new project folder, or finish global setup and choose later. Installing from a home/downloads/non-repository directory must not silently register that directory as a project. A detected current repository is a suggestion, not an automatic selection. After selecting or creating a project, Rush offers configuration and its reviewable dependency/provisioning plan. `rush install --agents all --memory on` completes without a project; explicit `--project <path>` selects that path. CLI, TUI and web expose the same project choices.

User workflow: **install/connect → select project → inspect/provision → full scan → aggregate/triage → hand to agent → verify fixes**. Automatic agent discovery covers all local known adapters and reports every detected unsupported integration; it must not silently redefine “all” as the currently working subset. Unknown future agents cannot be honestly guaranteed without a protocol/config adapter. An adapter registry and generic user-supplied stdio registration make that boundary visible and extensible.

Binding inputs: root `AGENTS.md`, `docs/templates/task-block-template.md`, [review ledger](../reports/phase-64-66-application-review.md), Phase 63 memory contracts, Phase 64 safety/result repairs, current catalog and installation scripts. Baseline `997b56e64bb2f72688cdd34252227a596f0fdb3d`; work off `main`. Plan does not authorize publishing assets, changing release versions, paid model use, installing hooks or modifying the user's real agent configuration during implementation tests.

## 2. Selected architecture and alternatives

| Decision | Alternatives | Selection / tradeoff |
|---|---|---|
| Beginner distribution | Editable uv checkout; pip/Python prerequisite; standalone release artifacts | Verified native artifacts for each supported OS/architecture. Larger release matrix, but no developer bootstrap prerequisite |
| Engine provisioning | Global arbitrary package installs; bundle every engine; managed per-engine environments | Rush-owned toolchains with exact package identities, selected per project and reused when compatible. Downloads are explicit and recoverable; quality engines remain external to Python package dependencies |
| Product execution | CLI-only wrappers; separate UI/MCP implementations; shared tools/workflows | Shared `src/rush/tools/` entry points with a single project/run backend. All surfaces use identical permissions, coverage and evidence |
| Run persistence | New database service; second memory database; existing AtomicFile + typed artifacts | Immutable run manifests/artifacts under project Rush storage, references in Phase 63 store. No server dependency or duplicate full payloads |
| Agent integration | Manual JSON snippets; one provider-specific route; adapter registry | Native client registration when supported, atomic format-preserving config otherwise; each adapter proves actual MCP handshake and memory capability |

Scanners, linters and formatters operate first. LLM requests receive bounded evidence and links for expansion, not repeated full logs. Existing continuity/transport and Phase 63 repair/intent/recipe APIs supply memory and feedback. No second agent framework, generic scheduler, benchmark framework or automatic Git hook installation.

## 3. Shared contracts every task must implement

### 3.1 Installation and connection

Production copyable commands, once corresponding release assets are published and validated:

```sh
curl -fsSL https://raw.githubusercontent.com/jamesdsizemore/rush-cli/main/scripts/install.sh | sh
```

```powershell
irm https://raw.githubusercontent.com/jamesdsizemore/rush-cli/main/scripts/install.ps1 | iex
```

These are planned installation contracts, not currently valid instructions for the existing editable-checkout scripts. Shell scripts download the OS/architecture release asset and checksum manifest, verify before extraction, install in a user-owned binary directory, and invoke the installed binary by absolute path with `install --agents all --memory on`. Preserve original cwd only as a possible repository suggestion, never an implicit `--project` argument. Prompt through the controlling terminal when available; streamed stdin or non-interactive installation must still complete global setup with project selection pending. They must work without `$PSScriptRoot`/script-directory assumptions. PATH setup is persistent and current-session limitations are explicit; installer itself must not depend on a new shell. A pinned version option selects a matching checksum manifest. Unsupported architecture fails before config mutation.

Supported release acceptance matrix: macOS arm64/x86_64, Linux x86_64/arm64 and Windows x86_64/arm64. If the packaging backend cannot produce one matrix member, that member remains an open implementation blocker, not an omitted platform. No runtime source checkout is required. Updates stage new binary/config changes and retain the last working installation until readiness passes.

Agent inventory records `agent_id`, executable/app identity, detected version, config scope/path, adapter version and state. States: `not_detected`, `detected`, `configured`, `restart_required`, `connected`, `unsupported`, `failed`. Only actual client/session evidence makes `connected`; a server self-handshake proves server health separately. Existing unrelated config and secrets are preserved, and secrets never enter receipts. Requested `all` discovers installed supported adapters, including documented Claude Desktop, Claude Code, Cursor, Windsurf and Zed, plus Codex; generic stdio configuration is available for others. Do not install coding agents themselves.

Memory readiness requires the actual store opens, project/user/session/agent scopes are bound, a synthetic scoped write/read/rollback health check passes and verifies absence without leaving test memory, and MCP memory tools are visible. MCP tool observations are captured through Phase 63's observation seam. Chat/session content outside Rush calls requires a supported native agent lifecycle integration with user consent; do not claim whole-chat collection merely because MCP was registered. If a client needs restart, offer its supported reconnect/restart action while preserving active sessions; report precisely what remains before collection becomes active.

### 3.2 Project, provisioning and full coverage

`project_id` is a durable UUID stored with the canonical physical root; display name is not identity. Git remote is descriptive, never authority. Two worktrees have distinct roots and run histories, with an optional common-repository relationship. Reopening an existing root returns its existing ID; moved roots require explicit relinking with identity checks. No filesystem escape or symlink alias creates duplicate/foreign authority.

Project operations are distinct: `add` registers an existing folder, `select` chooses a registered project for the current interface/session, `configure` changes that project's scan/memory/agent settings through a reviewable plan, and `create` creates a named folder at a user-selected parent and registers it. Create refuses an occupied destination; optional Git initialization requires explicit choice and creates no commit or hook. This defines Rush project creation, not a preselected application scaffold or generated framework. Global defaults and compatible cached toolchains can be reused; per-project settings, results and project memory stay isolated, with user memory sharing governed by explicit scopes. No-project global setup must not create project records or scanner installations accidentally.

Provision plans include detected languages/frameworks/workspaces, exact engine→package identity, manager/runtime/version/architecture, artifact URL/hash where downloaded directly, install destination, prerequisite project dependencies, proposed commands, side effects and required grants. Scanner distributions and relocatable runtimes install under Rush-owned directories; the explicitly granted non-relocatable system prerequisites use the exact §6.2 OS-manager routes. Project lockfiles are honored, never regenerated silently. Project dependency scripts/builds require explicit build permission; network/download/write permissions remain independent. Once a user authorizes the exact plan, do not ask again for every package. Plan identity changes invalidate that authorization.

Every catalog tool receives a disposition: `applicable`, `not_applicable`, `requires_input`, `unsupported`, or `excluded_by_user`. Every applicable planned execution ends `executed`, `unavailable`, `permission_blocked`, `failed`, or `cancelled`, and retains its child ToolResult. `complete` requires all applicable mandatory checks actually completed; `clean` additionally requires no findings above the requested threshold. Missing project prerequisites, engines and explicit target inputs are visible gaps. Destructive workflow tools such as release/cleanup are classified as non-scan operations with a reason; full scan does not publish releases or clean user files.

### 3.3 Run, findings and handoff

Run states: `planned → provisioning → running → completed | incomplete | failed | cancelled`; resuming creates a new attempt referencing the prior run rather than rewriting evidence. Immutable terminal run manifest contains project ID/root, source revision plus dirty-content identity, config hash, toolchain identities, permissions, file/ignore inventory, all dispositions, child results, timings, artifact references and totals. Shared `aggregate_results` behavior retains findings/versions/reasons; no `TypeError` retry.

Finding identity includes tool/engine/rule, normalized physical-project-relative path, location and stable evidence fingerprint. Group equivalent findings for display but retain every source finding and severity; do not deduplicate solely by message. Persist complete reports once; compact handoffs use IDs and exact expansion references with Phase 63 budget enforcement.

Handoff records selected agent, project/source identity, findings, desired acceptance checks, grants, memory references and token count. Delivery, acknowledgment, agent-reported completion and verified remediation are distinct states. Rescan compares equivalent tool/config/scope evidence and marks each finding `resolved`, `persisting`, `new`, or `unverified`; a missing engine cannot make a finding resolved. Optional repair runs use Phase 64 isolation and Phase 63 verification/memory contracts. No automatic commit, push or destructive rollback.
