# MC03 — Store evidence edges and consolidate duplicate episodes

Evidence record for Phase 63 workstream MC03 (`docs/phase-plans/phase-63-memory-capabilities-vibecoder-plan.md` §9, MC03.1-MC03.5). Owned production files: `src/rush/tools/memory.py`, `src/rush/memory/relations.py` (new), `src/rush/memory/consolidation.py` (new), schema additions in `src/rush/memory/store.py`. Owned test files: `tests/test_memory_relations.py`, `tests/test_memory_consolidation.py`.

## Schema addition (`store.py`)

One new additive table, alongside MC01's `artifact_version`/`memory_artifact_versions`/`memory_changes` and MC02's `memory_fts_candidates`/`memory_cursor_key`, none of which are touched:

- `memory_relations(sequence INTEGER PRIMARY KEY AUTOINCREMENT, source_id TEXT, source_version INTEGER, target_id TEXT, target_version INTEGER, kind TEXT, origin_ref TEXT, created_at REAL)` plus `idx_memory_relations_source`/`idx_memory_relations_target`. `CREATE TABLE IF NOT EXISTS` inside `_SCHEMA_SQL`'s existing `executescript()` call means an existing pre-MC03 store gets the table the next time it's opened — no `ALTER TABLE` migration or backfill needed, since it's a brand-new empty table (same idiom as MC02's `memory_fts_candidates`/`memory_cursor_key`).
- Endpoints are versioned (`source_id`/`source_version`, `target_id`/`target_version`), not "the current row", so a relation can go stale independently of the endpoint artifact being edited — `related_artifacts()` detects that by comparing the recorded version against `TypedArtifactStore.get_current()`.
- No new `TypedArtifactStore` methods were added. `relations.py`/`consolidation.py` reach the DB the same way `migration.py`/`expiry.py`/`maintenance.py` already do: `sqlite3.connect(str(store.db_path))` directly (never a private `store._connect()`), and `_write_version`/`store.write()`/`store.update_content()`/`store.get_current()`/`store.get_version_content()`/`store.search()` for everything that touches `memory_artifacts` — MC01/MC02's mutation and read paths are reused unchanged, never duplicated.

## `add_relation()` / `related_artifacts()` (new `relations.py`)

Both return a plain dict with a leading `"code"` key (`"OK"` or `"E_INPUT"`/`"E_NOT_VISIBLE"`), never raising for a business-rule rejection — the same contract `retrieval.py` established for MC02.

**`add_relation`** — one `BEGIN IMMEDIATE` transaction:
1. Rejects an unsupported `kind` before opening a connection at all. Supported kinds (§6.3, verbatim): `supersedes`, `contradicts`, `caused_by`, `fixed_by`, `validated_by`, `implements`, `depends_on`.
2. Checks both endpoints are real `(artifact_id, artifact_version)` pairs against `memory_artifact_versions` (the immutable version history, not just the current row — so a relation can still point at a since-superseded version).
3. For `supersedes` specifically (the one kind §6.3 requires acyclic), BFS's the existing `supersedes` edges from the proposed target back toward the proposed source; if a path already exists, the new edge would close a cycle and is rejected.
4. Only if every check passes does the `INSERT` run. A rejected edge (unsupported kind, unknown endpoint, or a cycle) never issues the `INSERT` at all — verified in `test_supersedes_cycle_rejected_atomically` by asserting `memory_relations` row count stays at 1 after inserting `a1@1 supersedes a2@1` then attempting the inverse `a2@1 supersedes a1@1`, an unsupported kind, and an unknown endpoint (four total attempts, one real row).

**`related_artifacts`** — breadth-first traversal from one seed:
- `depth`/`max_nodes` silently clamp to the §6.3 hard caps (2, 32) regardless of a larger request (`test_related_depth_node_and_token_caps`: a 5-node `supersedes` chain requested at `depth=10` only ever returns the depth-1 and depth-2 neighbors, never depth-3/4; a 40-leaf fan-out requested at `max_nodes=1000` returns at most 32 items with `complete=False`).
- Every discovered neighbor is revalidated against the caller's `session_allowlist` and its edge's recorded endpoint version against the neighbor's *current* version (`get_current()`, never a cached/earlier snapshot) — a denied, missing, or version-changed neighbor is dropped silently: no ID, count, or source name appears anywhere in the response (`test_related_hides_denied_neighbors` asserts the full serialized JSON doesn't contain the denied artifact's ID or content). This mirrors `expand_artifact()`'s identical-body denial precedent from MC02 (§9.0) rather than inventing a new disclosure shape.
- A version change on a linked endpoint invalidates that edge on the next traversal — `test_relation_version_change_invalidates_active_evidence` links `a1@1 fixed_by a2@1`, confirms `a2` is related, then `update_content("a2", ...)` (bumping it to version 2), and confirms the same traversal now returns nothing for that edge. No separate "invalidated" flag is emitted; the edge is just excluded, the same way a denied neighbor is.
- Shares the same token/byte budget shape as `recall_page()`/`expand_artifact()` (`DEFAULT_MAX_TOKENS=2048`, `DEFAULT_MAX_BYTES=8192`): a candidate is only appended if the trial-serialized `items` list still fits both caps; a budget too small to fit even one candidate returns `items=[]`, `complete=False`.
- `complete=False` means the node cap or the token/byte budget stopped traversal before every reachable-within-depth neighbor was included — never that something was denied or invalidated (that's indistinguishable from "never linked" by design, per §6.3's non-disclosure requirement).

## `consolidate_episodes()` / `summary_is_current()` (new `consolidation.py`)

Groups `episodic` artifacts matching one `symptom` by an exact canonical `(symptom, condition, attempt, outcome)` tuple (`condition` canonicalized via `json.dumps(..., sort_keys=True)`) — never a fuzzy/semantic match, per §6.3 ("semantic similarity may propose a group but cannot merge contradictory conditions automatically"). Candidates come from `store.search("episodic", symptom)` (MC01/MC02's existing FTS path over `memory_fts`, not a new query surface), filtered to `session_allowlist` (fail-closed on empty, `"E_PERMISSION"`, matching `TypedArtifactStore.recall()`'s precedent) and to episodes whose canonical tuple's `symptom` field matches exactly.

- The largest exact-duplicate group becomes the summary's repeated majority (`repetition` = its size); every other member — a differing condition, attempt, or outcome under the same `symptom` — is recorded as a distinct `exceptions` entry, never folded into the repetition count. All members (majority + exceptions) are listed in `member_ids`/`member_versions`; none are dropped.
- `test_duplicate_summary_preserves_originals_and_exception`: three identical failed-timeout episodes plus one changed-condition success — all four IDs retained, `repetition == 3`, the success is the sole `exceptions` entry, and every original row's stored bytes (`store.get_version_content(id, 1)`) are byte-identical before and after consolidation (consolidation only ever calls `store.write()` to insert a brand-new summary artifact; it never calls `update_content`/`delete` on a member).
- `test_contradictory_conditions_are_not_merged`: two episodes sharing `symptom`/`attempt`/`outcome` but a contradictory `condition` produce two size-1 groups (`repetition == 1`, one `exceptions` entry), never a merged `repetition == 2` — this falls directly out of exact-tuple grouping, since a differing `condition` always produces a differing canonical tuple.
- Trust: the summary inherits the members' own `trust_tier` only when every contributing member (majority + exceptions) agrees; a mixed group, or an agreeing tier that happens to be `"STATED"` (which `MemoryArtifact.write()` refuses to insert directly — promotion is the only path to `STATED`), falls back to `"DERIVED"`. Repetition count never upgrades this — `test_repetition_cannot_promote_trust` consolidates three identical `DERIVED` episodes and asserts the summary stays `"DERIVED"`, explicitly `!= "STATED"`, regardless of the 3x repeat.
- `summary_is_current(store, summary)` — a small standalone check, not persisted state — re-fetches every `member_versions` entry's *current* `artifact_version` and returns `False` on any mismatch. `test_duplicate_summary_preserves_originals_and_exception` asserts `True` immediately after consolidation, then edits one member via `store.update_content(...)` and asserts `False` afterward (§6.3: "an edited member invalidates the summary").

## `MemoryTool` wiring (`tools/memory.py`)

Three new `MemoryOperation` values, each following MC02's request-envelope pattern (`request` dict, unknown-key rejection, field-type validation, `_envelope_result()` wrapping):

- **`link`** (`_LINK_REQUEST_KEYS = {source_id, source_version, target_id, target_version, kind, origin_ref}`) — gated on `cache_write` via the same `_WRITE_PERMISSION`/`check_permissions()` pattern as `write`/`promote`/`maintain`, checked before `request` is even inspected. Calls `relations.add_relation()`.
- **`related`** (`_RELATED_REQUEST_KEYS = {id, version, depth, max_nodes, max_tokens, max_bytes, encoding}`) — a read operation, no `cache_write` gate, scoped by the existing top-level `session_allowlist` parameter (same as `ask`/`recall`/`expand`). Calls `relations.related_artifacts()`.
- **`consolidate`** (`_CONSOLIDATE_REQUEST_KEYS = {symptom}`) — gated on `cache_write` (it writes a new derived summary artifact via `consolidate_episodes()` → `store.write()`), same as `link`. Calls `consolidation.consolidate_episodes()`.

All three always require `request` (no legacy no-request fallback, since these are brand-new operations with no pre-MC03 callers to preserve compatibility for — unlike `ask`/`recall`/`list`, which MC02 kept a `request=None` legacy path for).
