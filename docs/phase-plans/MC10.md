# MC10 — Compare current failure to last successful behavior

Implements the `memory_behavior_success` last-success index in
`src/rush/memory/store.py` (`TypedArtifactStore.write_pass()`/`get_behavior_success()`/
`find_any_behavior_success()`), `record_behavior_success()`/`compare_last_success()`/
`record_cause_experiment()` in `src/rush/memory/experience.py`, and the
`last_success_diagnose` operation in `src/rush/tools/memory.py` (MemoryTool).

## Schema and transactional pointer

`memory_behavior_success` is an additive table (never touching MC01's
`memory_artifact_versions`/`memory_changes` or MC03's `memory_relations`), keyed
`(namespace, behavior_id, runtime_digest)` and holding the pointed-at observation's
`artifact_id`/`artifact_version`. `runtime_digest` (`behavior_runtime_digest()`) is a
digest of `runtime`+`platform` only -- code/config/dependency/engine are separate
comparison subjects stored inside the pointed-at artifact's `conditions`, never part of
the key, so a code-only change stays comparable under the same pointer while a genuinely
different runtime/platform is a separate entry.

`TypedArtifactStore.write_pass()` is the only writer of `memory_behavior_success`. It
reuses `_prepare_write()`/`_insert_row()` -- the exact same sanitize/insert/version/
changes-audit body `write()` uses -- and inserts the pointer row inside the same
`BEGIN IMMEDIATE` transaction as the passing observation it points at: the only SQL
statement that writes `memory_behavior_success` lives inside `write_pass()` itself,
immediately after `_insert_row()` in the same transaction, so a fresh observation row
always accompanies each pointer move (verified-by: `grep -n "memory_behavior_success"
src/rush/memory/store.py` -- the sole `INSERT` is inside `write_pass()`; plain `write()`/
`write_observation()`, the only routes reachable from a cache hit, skip, tag, or caller
label, contain no reference to that table at all).

## Diagnosis

`compare_last_success()` looks up the exact-environment pointer, reads back its
`conditions` from `memory_artifact_versions` (`get_version_content()`), and diffs each
comparison subject independently: `code_changes`, `config_changes`, `dependency_changes`
(each `None` unless that one digest differs) and `engine_changes` (populated on any
`engine`/`engine_version` difference, including an engine going unavailable --
distinguished from `code_changes`, never conflated with it). `cause_state` always
defaults to `"candidate"`; it becomes `"reproduced"` only when a prior
`record_cause_experiment()` call recorded a controlled comparison against this exact
`baseline_ref` with `cause_state="reproduced"` (found via `store.search("episodic", ...)`
over recorded `cause_experiment` artifacts -- correlation alone never upgrades it).
`historical=True` falls back to the most recent pointer under any runtime digest when no
exact-environment match exists, reporting `environment_compatible=False` for it.

`record_cause_experiment()` only reports `cause_state="reproduced"` when
`control_receipt_ref` is a real receipt reference *and* `outcome_changed=True`; a missing
receipt (e.g. an unavailable engine whose control run never executed) or an unchanged
outcome always stays `"candidate"`.

## Test fixtures and scoped-pointer/controlled-run receipts

All 7 tests in `tests/test_memory_last_success.py` pass (`11 passed` together with
`tests/test_memory_verify_attempt.py`).

- **`test_success_is_per_behavior_and_environment`**: records Upload passing under
  `python3.11`/`darwin`, then a plain observation of Upload *failing* -- the pointer stays
  at the original pass artifact (`store.get_behavior_success(...) == (passed.id,
  passed.artifact_version)`). Recording Download under `python3.12`/`linux` creates its own
  independent entry; Upload's `python3.11`/`darwin` pointer is unchanged and no entry
  exists for Upload under Download's runtime digest.
- **`test_skipped_or_cached_check_cannot_advance_success`**: a cache-hit/tag-only
  observation with no `record_behavior_success()` call never creates a pointer
  (`get_behavior_success(...) is None`); after a real pass establishes one, a later
  skip/cache observation leaves it pointing at the original pass receipt.
- **`test_code_dependency_and_config_changes_are_distinguished`**: three isolated
  comparisons (only `code_digest`, only `dependency_digest`, only `config_digest` changed)
  each populate exactly one of `code_changes`/`dependency_changes`/`config_changes`; the
  other two and `engine_changes` stay `None` every time.
- **`test_unavailable_engine_is_not_application_regression`**: current conditions set
  `engine`/`engine_version` to `None` with everything else identical to the baseline.
  `engine_changes` reports the baseline `pytest`/`8.0.0` vs. current `None`/`None`;
  `code_changes`/`config_changes`/`dependency_changes` stay `None` and `cause_state` stays
  `"candidate"` -- an unavailable engine is never treated as an application-code
  regression.
- **`test_only_controlled_reproduction_confirms_cause`**: a code-digest diff against the
  baseline reports `cause_state="candidate"`. Recording a cause experiment with
  `control_receipt_ref=None` (an unavailable-engine control run that never executed)
  returns `"candidate"` even with `outcome_changed=True`, and a follow-up
  `compare_last_success()` call is still `"candidate"`. Only a real receipted run
  (`control_receipt_ref="receipt:pytest-run-42"`, `outcome_changed=True`) flips the
  recorded experiment and the subsequent `compare_last_success()` call to
  `"reproduced"`.
- **`test_later_failure_does_not_destroy_last_success`**: after a real pass, a plain failed
  observation carrying a different `code_digest` in its own content leaves the pointer
  intact (`get_behavior_success(...)` still resolves to the original pass artifact), and a
  subsequent `compare_last_success()` call's `baseline_ref` still names that same original
  artifact id/version.
- **`test_memory_tool_last_success_diagnose_operation_returns_diagnosis`**: exercises the
  `MemoryTool` wiring end to end (`operation="last_success_diagnose"`, request fields
  `behavior_id`/`conditions`); the tool's `raw.data` envelope matches
  `compare_last_success()`'s direct return shape (`config_changes` populated,
  `code_changes` `None`, `cause_state="candidate"`).
