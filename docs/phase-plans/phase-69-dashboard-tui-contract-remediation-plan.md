## 3. Contract clarifications (supersede named Phase 66 §3 clauses only)

These resolve Phase 66 §0's rows 21-24 (internal contract ambiguities and one ordering defect in the contract's own wording). Nothing else in Phase 66 §3 changes.

**Supersedes Phase 66 §3.2/§3.7 Bearer-auth clause (row 21).** Bearer authentication is bootstrap-exchange-only: a one-use credential, valid for first exchange or 5 minutes, after which only the cookie session or a freshly issued `--reconnect` bootstrap authenticates. There is no separate long-lived programmatic credential. A programmatic client that needs a new session calls `rush dashboard --reconnect --json` for a fresh one-use bootstrap URL, the same mechanism a human reconnect uses. This matches already-shipped behavior (`server.py:1535`) rather than adding a new credential surface.

**Supersedes Phase 66 §3.7 cross-server-isolation claim (row 22).** "A server's auth/state cannot affect another server" means cooperating Rush-launched servers never collide (distinct random cookie names, distinct auth/session state per `DashboardContext`). It does not claim isolation from an untrusted, non-Rush, same-host service on another port — host-only `Path=/` cookies are not port-scoped, and no cookie mechanism makes them so. This is a stated, accepted threat-model boundary, not a defect to code around.

**Supersedes Phase 66 §3.1/§3.6 memory-write "scope" clause (row 23).** `scope` in the browser/TUI memory contract means an explicit **ownership** field distinct from the existing `subject` field on `MemoryArtifact` (`src/rush/memory/store.py:71-87`, read directly this session to carry no ownership field today — `subject` is a `MemorySubject` enum value such as `domain_knowledge`, not an owner). Every memory write from the dashboard/TUI must carry `owner_scope: {kind: "user"|"project"|"session"|"agent", id: str}` in addition to `subject`; P69-07.2 adds this as a real, migrated `MemoryArtifact` field, not an HTTP-layer-only tag.

**Supersedes Phase 66 §3.4 animation-cancellation ordering (row 24).** "Cancel prior animations, retain current computed transform as next animation's start" is ordered wrong as written — cancelling first removes the animated effect before its visible intermediate position can be read back. The corrected order, which P69-05.2 implements: capture the live visual transform first (read the actual current on-screen position, not the target/final value), then call `cancelActiveAnimations()`, then start the new animation from the captured value. This clause is the resolution P69-05 implements; P69-05 cites this clause directly rather than restating it.
