# Phase 68 — One-and-Done Install

## 1. Why this phase exists

Real end-to-end testing this session (2026-09-13/14) found the actual path from "download rush" to "rush is checking my code" requires four separate typed commands, each with flags never documented anywhere a new user would find them:

```
curl -fsSL .../install.sh | sh
rush init .
rush governance sync
rush setup . --install --allow-download --allow-network --allow-build --allow-cache-write
```

Explicit requirement from the maintainer, verbatim, final: a user should only ever have to run one command (the install line itself, or `rush install` — never longer than two words) or click one button. That single action installs into the current project, activates and serves the MCP server, activates and serves all available CLIs, activates and serves the memory system, and launches the web dashboard. No picker, no prompt, no second command, no wizard.

**Extended requirement (2026-09-14):** the dashboard must stay reachable without the user doing anything again — not after closing the terminal session, and not after restarting the machine, including before that user logs back in. `rush install` registers a real, boot-level OS autostart entry. Registering it requires one elevated-privilege prompt during `rush install`. That elevation is scoped to this one registration step, not the rest of install. The TUI (`rush ui`) is not part of this — it is a foreground interactive terminal program; there is nothing sensible to "autostart" about it.

**Extended requirement (2026-09-14, round 2):** the install experience itself must be graphic, animated, engaging, and explanatory — a live, styled progress display naming each step as it runs, not a plain scrolling log — **covering the whole install line, including the shell-script download/verify stage that runs before Python code exists, not only the `rush install` (Python) portion** (round-5 finding R5-16: an earlier draft's animation only started once `InstallTool.run` began, leaving the initial binary download silent).

**Phase 66 alignment, corrected after round-5's semantic-drift scan (2026-09-15):** Phase 66's own text requires the browser shell to become interactive before long work (a scan) completes, not after (`phase-66-interactive-tui-and-local-web-plan.md:48,112`, verified-by: read this session). An earlier draft of this plan opened the browser only after the triggered scan finished, which both contradicted that requirement and forced a "type `rush dashboard --reconnect`" fallback into the common path if the bootstrap TTL was ever at risk — a real, if narrow, violation of "no second command." The corrected flow in P68-04 below (reordered again in round 8, see below) has the installer register the project and start the scan on its own session first, then opens the browser — landing the user directly on this project's live view before the scan *completes*, matching Phase 66's actual requirement (interactive before long work finishes, not necessarily before it starts), and the user watches the scan run live in the UI exactly as Phase 66 already specifies — this removes the timing conflict and the fallback-as-primary-path problem at the same time, not just the wording of either.

**Process-ownership architecture, current after rounds 1-5 adversarial review (2026-09-15):**

- **The OS-registered service process is the only thing that ever calls `server.serve_forever()`.** `rush install` itself never runs a long-lived server loop. Manually running `rush dashboard` (no `--service` flag) still runs its own separate, foreground `serve_forever()` loop exactly as it does today (`cli.py:1244`) — the boot service and a manually launched dashboard are two independent, coexisting `create_dashboard_server` callers.
- **What launchd/systemd/Task Scheduler register is a small, privileged, long-lived supervisor process ("the wrapper"), installed as a SEPARATE, root/SYSTEM-owned artifact — never the same mutable file `rush install` writes to the user's own install directory.** This is the round-5 correction, closing a real local-privilege-escalation hole in round 4's design (round-5 finding R5-01, CRITICAL: registering the same user-writable `rush` binary to run as root meant any process running as the installing user could replace that file and have its own code executed as root on the next wrapper restart or reboot):
  - **At registration time (the one elevated `rush install` prompt), the installer copies the current `rush` binary to a separate, root-owned, non-user-writable path** — macOS: `/Library/PrivilegedHelperTools/com.rush.wrapper` (Apple's own established convention for exactly this kind of privileged helper); Linux: `/usr/local/libexec/rush-wrapper`, mode `0700`, owned by `root:root`; Windows: a copy under a location whose ACL grants write only to `Administrators`/`SYSTEM`, e.g. `%ProgramFiles%\Rush\rush-wrapper.exe`. This copy — not the user-writable `install_dir/rush` — is what every platform's native service manager registers and executes with elevated privilege.
  - **An ordinary, unprivileged `rush install` re-run never touches this privileged copy.** It only replaces the user-writable `install_dir/rush` binary the wrapper's *child* execs (after that child has already dropped to unprivileged status — see below). Updating the privileged wrapper artifact itself requires a fresh, explicitly elevated registration step (the same one-time `sudo`/UAC prompt) — a deliberate trust-boundary choice: the wrapper is designed to be minimal and stable enough that it rarely needs updating, and any update to it is a conscious, re-elevated action, not a side effect of routine `rush install` re-runs.
  - **The wrapper forks the child process and drops privilege completely before that child ever runs code from the user-writable binary.** POSIX, platform-conditional verification (round-7 finding: `os.getresuid`/`os.getresgid` do not exist on macOS — verified-by: ran `python3 -c "import os; print(hasattr(os,'getresuid'), hasattr(os,'getresgid'))"` this session, printed `False False`): `os.setgroups([])` → `os.setgid(installing_gid)` → `os.setuid(installing_uid)`, in that exact order → on Linux, verify via `os.getresuid()`/`os.getresgid()` that real/effective/saved UID and GID all now match the installing user's values; on macOS, where those calls are unavailable, verify via `os.getuid()`/`os.geteuid()`/`os.getgid()`/`os.getegid()` (both real and effective IDs now match the target — the strongest check the platform's Python exposes) → close all open file descriptors except the three the child needs (stdin/stdout/stderr redirected to its own log) → reset the environment to the installing user's own baseline → set the working directory → only then `execve` into `install_dir/rush dashboard --service ...`. Any failure or unconfirmed state at any step aborts the exec attempt and counts as a child-start failure. **Windows privilege drop, corrected after round 7 (finding: `WTSQueryUserToken` requires an active, logged-in interactive session, which directly contradicts this same phase's own before-login-availability requirement — an earlier draft's mechanism could never satisfy both at once):** the wrapper runs as `LocalSystem`, and at registration time creates a dedicated Windows virtual service account (`NT SERVICE\RushDashboardChild`) with no interactive logon rights, granted explicit read/write ACL access only to the data root and registered project directories. The child launches under this virtual service account via the Service Control Manager (not `CreateProcessAsUser`+`WTSQueryUserToken`) — a mechanism that, unlike session-token queries, needs no logged-in user and no stored password, and is genuinely available before login, matching the real availability macOS/Linux's `setuid`-based drop already has.
  - **The wrapper stays alive and supervises the child directly**, in-process, rather than relying on the native OS restart setting to restart each crash. It owns the consecutive-crash counter itself, persisted next to the wrapper artifact itself (root-owned, not user-writable) so the count survives a wrapper restart, and the give-up threshold (5). A failed `execve` (e.g. the child binary is missing) counts as a crash for this same counter — there is no separate case for "binary missing" versus "binary present but exits immediately," both simply increment the same counter. Native OS restart settings (macOS `KeepAlive`, Linux `Restart=on-failure`, Windows `RestartCount`) now bound **wrapper** crashes only — a separate, much rarer event than child crashes, since the wrapper is deliberately tiny (fork/wait/count/restart-child/self-deregister and nothing else) — not every child restart attempt.
  - **On exhaustion, the wrapper stops restarting via a clean exit code, then finishes deregistration through a detached helper it spawns and does not wait on — corrected again after round 7, which found deleting the registration file alone does not unload an already-loaded service (macOS `launchd` and, per the same principle, Linux's live unit state keep a job "loaded" independent of whether its on-disk definition file still exists; only `launchctl bootout`/`systemctl disable`+stop/`schtasks /Delete` genuinely deregister a loaded job, and calling any of those synchronously against the wrapper's own still-running process risks killing it mid-cleanup, the exact problem round 5 already found once):** the wrapper stops the child if one is running, then exits with status code 0 — every native restart setting this plan specifies (macOS `KeepAlive={"SuccessfulExit": false}`, Linux `Restart=on-failure`) restarts on a non-clean exit only, so a status-0 exit stops the restart loop immediately, with no race against the process's own removal logic, because no further removal logic needs to run in-process at all. Before that exit, the wrapper deletes the on-disk plist/unit file and spawns a detached, fire-and-forget child process (not waited on, so it cannot block or be killed by the wrapper's own exit) that runs the platform's real full-deregistration command (`launchctl bootout system/<label>`, `systemctl disable <unit>`, `schtasks /Delete`) — by the time that detached process runs, the wrapper has typically already exited, so there is no running process for the deregistration command to conflict with. `rush uninstall` (P68-06) uses a different, simpler sequence available to it because it is a separate, human-invoked process that can wait synchronously: it sends the wrapper a `shutdown` command (below) and waits for it to actually exit before removing the plist/unit file and the wrapper artifact directly, with no detached-process trick needed.
  - **A crash-restart of the wrapper itself is bounded only by each platform's native, standard restart throttling (macOS `ThrottleInterval`, Linux `RestartSec`, Windows `RestartInterval`) — the same guarantee every other long-running system daemon on that platform has (systemd's own PID 1, `sshd`, `nginx`'s master process), not a bespoke self-removal mechanism.** This is a deliberate, honest design boundary, not an oversight: the wrapper exists specifically to give the *child* (which risks a missing or broken `rush` binary) a bounded, self-removing retry path; bounding the wrapper's own retries the same way would require a second, more-privileged supervisor watching the first, which just relocates the same question one level up without actually resolving it. A wrapper that is crash-looping at all is a sign of a genuine system problem visible through the OS's own normal daemon-health surfaces (Console.app/`launchctl list`'s exit-status field on macOS, `systemctl status`/the journal on Linux, Event Viewer on Windows), the same place any other misbehaving system daemon would surface.
  - **On a clean, intentional stop** (the wrapper receiving its own stop signal — from `rush uninstall`, or an OS shutdown), the wrapper stops the child if running and resets its counter to zero before exiting.
- P68-05 registers the wrapper (once, from `rush install`) and starts it immediately, not only at the next boot.
- **Every descriptor the wrapper's child (`rush dashboard --service`) writes carries an explicit `service_mode: true` field** so `rush install`'s own discovery in P68-04 selects specifically the boot service's descriptor — never whichever descriptor happens to be newest-and-alive, which could be a manually launched, terminal-bound `rush dashboard`.
- **P68-04 (the install-triggered scan) never touches an in-process registry.** `rush install` becomes an authenticated HTTP client of its own (already-running) boot service, per the exact contract in P68-04 below — opening the browser as soon as the project is registered and reachable (Phase 66 alignment, above), sourcing each `expected.*` field from the real, specific response that actually carries it rather than assuming a uniform shape, and confirming scan publication via a durable per-run check rather than a "most recently published" pointer that a later, unrelated publication could race past.
- **Credential handling:** no bootstrap/session secret ever reaches the boot service's own persistent log, the wrapper's own log, or any file. `rush install`'s own short-lived, foreground, user-attended terminal may print its own one-time launch URL to its own stdout and open the browser automatically, exactly as `dashboard_cmd` already does today — never to a file, never to `--json` output.

## 3. Scope

**In scope:** `rush install` does everything in one shot when run from inside a project directory with no arguments: registers the current directory as the project, detects its stack, writes `rush.toml`, syncs governance rules for targets it's entitled to write, installs missing engines, connects every detected agent's CLI, activates memory, ensures the privileged wrapper supervisor and boot-level dashboard service are registered and running, registers the project against that running service, opens the dashboard in a browser as soon as it's reachable, and drives a real scan through to real, durably-proven completion the user watches happen live in the already-open dashboard. The entire run — including the shell-script download/verify stage — displays visible, explanatory progress, never blocking on typed input anywhere. A companion `rush uninstall` stops the wrapper/service and removes the autostart entry.

**Out of scope:** the `--allow-*` permission-flag architecture shared by other CLI commands. `rush setup`, `rush init`, and `rush governance sync` remain available standalone. `rush ui` is never autostarted. `rush uninstall` never deletes registered projects, `rush.toml`, or memory data. System-wide, pre-boot, multi-user daemon behavior beyond P68-05/P68-06 is out of scope. Updating the privileged wrapper artifact itself requires a fresh elevated registration, not an ordinary `rush install` re-run — a deliberate trust-boundary choice, not a gap.

**Governance policy — unchanged permanent-ownership rule (round 4), with round 5's crash-safety and hash correctness fixed:**

- A per-project state file (`.rush/governance-sync-state.json`) records, per target path, whether this mechanism owns it and (if owned) the SHA-256 of the bytes it actually wrote there.
- A target with no on-disk file at all: written, marked `owned: true`.
- A target that already exists on disk with no ownership record: permanently marked `owned: false`, skipped now and on every future sync, never auto-adopted.
- A target marked `owned: true` whose on-disk hash still matches the last-recorded value: re-synced when the canonical `AGENTS.md` changes.
- A target marked `owned: true` whose on-disk hash no longer matches: skipped, reported `governance_skipped_user_edit`.
- **Write ordering, closing round 5's crash-window finding (R5-14):** for a target being written, the target file's own content is written and atomically renamed into place *first*; the ownership-state record (recording the hash of exactly those written bytes, computed from the same buffer, not `SyncResult.sha256`'s canonical-source hash) is only updated *after* that rename succeeds. If the process crashes between the two, the on-disk target holds the correct new content but the state file still reflects the old hash — the next run sees a hash mismatch and treats it as `governance_skipped_user_edit` (safe: it never re-overwrites, it just conservatively stops managing a target whose state got out of sync, which self-heals the next time that target's content is deliberately reset to match a fresh sync).
- `AgentsMdSynchronizer.sync_all()` writes every target in one transactional call with no selection — P68-02 GREEN adds a target-filter parameter (or equivalent per-target write method) to the synchronizer itself, computing each target's write/skip decision from the state file above before calling in, and performs the state-file update as a separate step immediately after, per the ordering above.

### P68-05 — Root-owned wrapper artifact, complete privilege drop, real self-removal ordering, and boot-level OS registration (macOS, Linux, Windows)

**stop_if:** on macOS, `spctl -a -vv <binary>` must report an accepted, notarized verdict before building the macOS half; Linux/Windows can proceed regardless.

**Wrapper artifact and installation, per §1's corrected trust boundary:**

- At registration time, `rush install` copies the current `rush` binary to a separate, root-owned path (`/Library/PrivilegedHelperTools/com.rush.wrapper` on macOS; `/usr/local/libexec/rush-wrapper` mode `0700` root-owned on Linux; an admin-only-writable path under `%ProgramFiles%\Rush\` on Windows) and registers **that** path, invoked with `--wrapper`, with each platform's service manager — never the user-writable `install_dir/rush`.
- The consecutive-crash counter's state file lives alongside this same root-owned artifact (not in any user-writable location), written via write-to-temp-file-then-atomic-rename (the same `os.replace()` pattern `_atomic_install_binary` already uses elsewhere in this repo). Content: `{"consecutive_failures": N, "last_child_started_at": <ISO8601 or null>}`. On a fresh, first-ever wrapper start (no state file present at all), treat as `consecutive_failures: 0`. On any later start where the state file is present but unreadable/corrupt, fail closed: log the corruption plainly and treat it as an already-exhausted state (remove the registration and exit) rather than silently resetting to zero, since a corrupt state file is itself evidence of an interrupted crash and resetting could mask a real ongoing loop; recovering from this requires a fresh `rush install`/`rush uninstall`-then-reinstall, which is an acceptable, rare, explicit recovery path for a state that should not occur under normal operation.
- **Threshold semantics, pinned exactly (round-5 finding R5-07: "5" and "6th" were inconsistent):** the wrapper permits a child start whenever `consecutive_failures < 5`. After a child exits non-cleanly, the wrapper increments `consecutive_failures`, persists it, and only then decides whether to start another child (if still `< 5`) or remove its registration (once `== 5`) — so exactly 5 total child-start attempts ever occur before removal (the very first attempt counts toward this same total, not just ones after an initial crash), and "on the 6th" in test names below means the 6th *attempted* child start, which is the one that never happens because removal occurs first. `consecutive_failures` resets to 0 the moment a child has been running continuously for a fixed healthy-uptime window (5 minutes) or on a clean, intentional stop.
- **Control channel — a small Unix-domain-socket (POSIX) / named-pipe (Windows) command channel, permission-restricted to the installing user (POSIX: socket file mode `0600` owned by that user; Windows: named-pipe ACL restricted to that same account) — redesigned after round 5's pending-restart-race finding (R5-06), with a fourth command added after round 7:** `stop` unconditionally transitions the wrapper into a **paused** state — it stops the current child if one is running *and* cancels any pending scheduled restart, regardless of whether a child happens to be running at the exact moment `stop` is received — and only acknowledges the command once genuinely paused (no restart will occur until a matching `resume`). `resume` exits the paused state and restarts a child immediately if none is running. `status` reports current state (running/paused/counter value) for diagnostics. `shutdown` (round-7 addition) stops the child if running, then exits the wrapper process itself with status 0 — distinct from `stop`, which only pauses; `shutdown` is what `rush uninstall` (P68-06) uses, since uninstall genuinely wants the wrapper process gone, not paused. This channel is a local control surface, not a network one — it is never exposed beyond the local machine, and its permission bits are the full authentication model (matching how the rest of this repo's own local IPC, the per-server descriptor file, is already secured).
- **Exhaustion ordering — corrected after round 5 (R5-04): remove-then-exit, never stop-then-remove.** On reaching the threshold: (1) remove the OS registration first (delete the plist, or `systemctl disable` plus delete the unit file, or `schtasks /Delete` — a pure metadata operation on the registration itself, not on the running process); (2) stop the child if one is running; (3) the wrapper process simply exits normally. Because step 1 already guarantees nothing will restart it, no synchronous "stop myself" call against the wrapper's own process is ever needed or attempted.
- **POSIX privilege drop, the complete sequence (round-5 finding R5-02):** `os.setgroups([])` → `os.setgid(installing_gid)` → `os.setuid(installing_uid)` → verify via `os.getresuid()`/`os.getresgid()` that all three ID slots match the target on both calls → close all file descriptors except the three redirected to the child's own log → reset environment to the installing user's baseline → set working directory → `os.execve(install_dir/rush, ["rush", "dashboard", "--service", "--data-root", data_root, "--port", port], clean_env)`. Any failure anywhere in this sequence aborts the exec attempt and is counted as a child-start failure.
- **Windows privilege drop (round-5 finding R5-03 — this corrects an earlier draft's incoherent mix of "privileged wrapper" and "unprivileged S4U task" into one real mechanism):** the wrapper runs as `LocalSystem` via an ordinary Scheduled Task principal — no special DACL grant needed for self-management, since `LocalSystem` can always manage its own task. To launch the child unprivileged, the wrapper calls `WTSQueryUserToken` for the installing user's active session (the documented mechanism a SYSTEM service uses to obtain that user's own token without their password) and launches the child via `CreateProcessAsUser` with that token. If no such session exists (nobody is logged in), the child does not start, and this is surfaced plainly rather than silently retried as if it were an ordinary crash.
- **`--service`/`--wrapper` Click dispatch, an explicit mode-validity matrix (round-5 finding R5-09; corrected again in round 7, which found the existing `if reconnect: ...; return` branch, `cli.py:1178-1182`, is the first real logic in `dashboard_cmd`'s body — an earlier draft's "add the mutual-exclusion check right after it" would run the new check *after* that branch had already returned for a `--reconnect` call, letting `--reconnect --service`/`--reconnect --wrapper` silently fall through to ordinary reconnect behavior instead of being rejected):** `--service`, `--wrapper`, and plain foreground invocation (neither flag) are mutually exclusive on `dashboard_cmd`. The mutual-exclusion check runs as the *first* statement in the callback body — before the existing `if reconnect: ...; return` branch, not after it — so every invalid combination, including one involving `--reconnect`, is rejected (`click.UsageError`) before any side effect, including that branch's own early return. `--service` requires `--data-root` to also be given; it is meaningless alone. `--wrapper` also requires `--data-root` (it passes this straight through to the child it execs) and rejects a positional `path` argument if one is given.
- **Data-root propagation, corrected again after round 8 — the round-7 `functools.partial`/import-removal design does not actually enforce anything (round-8 finding, independently checked this session: `functools.partial(..., data_root=value)` only supplies a default keyword a caller can still override; a bare unbound call after removing the import raises `NameError`, not `ImportError`, so nothing actually stops a future import from reintroducing the bare function; and 24 of 32 real call sites the round-7 AST check found are inside dispatcher functions — `_dispatch_provision_plan`, `_dispatch_provision_apply`, `_dispatch_scan_cancel`, `_dispatch_handoff_preview`, `_dispatch_handoff_send`, `_dispatch_memory_edit`/`_archive`/`_delete`/`_promote`, `_dispatch_data_export` — that don't have `ctx` in scope at all, so binding methods onto `ctx` never reaches them regardless of how the binding itself works):** the real fix is explicit parameter threading, not an indirection trick. `_dispatch_scan_action` (`server.py:707-743`, verified-by: read this session) is the single central dispatcher every one of these operations already routes through, and it already receives `ctx` — three of its callees (`_dispatch_scan_start`, `_dispatch_scan_resume`, `_dispatch_rescan`) already take `ctx` as their first parameter, confirming this is the established real pattern in this codebase, not a new one. - **Binary replacement, updated for the split wrapper/child model — the "old privileged code keeps running" problem (round-5 finding R5-05) is structurally smaller now, since the wrapper artifact is not what ordinary `rush install` replaces:** for the common case (replacing `install_dir/rush`, which only the unprivileged child execs), `install.sh`/`install.ps1` and `InstallTool.run`'s existing `_atomic_install_binary` call each gain an identical-bytes short-circuit, and — whenever a wrapper is registered at all, **regardless of whether it currently reports a child running** (round-7 finding: an earlier draft's "if the wrapper reports a child running" conditional skipped the pause step entirely during the exact mid-crash-backoff window that same conditional was supposed to protect, since no child is running during backoff) — send `stop` over the control channel and wait for the paused acknowledgment (a trivial, immediate acknowledgment when no child happens to be running), replace the binary, run the existing post-install probe, then send `resume` (on probe failure: restore the backup binary, then still send `resume`, so a good binary is restarted rather than left down). Because the child is unprivileged, this is now an ordinary file replacement with no privileged-process-holding-the-file complication. Updating the separate, root-owned wrapper artifact itself is out of scope for an ordinary `rush install` re-run (§3) — it only happens via a fresh, explicitly elevated registration.

**Windows lifecycle, redesigned after round 8 (finding: `WTSQueryUserToken` cannot run before login, and separately, the Service Control Manager only starts a process that implements `StartServiceCtrlDispatcher` — swapping the account alone does not give an arbitrary child process that entry point):** on Windows only, the child is *also* a real, separately registered Windows service (`sc.exe create ... obj= "NT SERVICE\RushDashboardChild"` at registration time — SCM handles running it under that virtual account directly, no token-passing code needed at all), and `rush dashboard --service` implements `StartServiceCtrlDispatcher` so it is a valid SCM service target. The wrapper's Windows-specific responsibility becomes starting/stopping/monitoring the child **service** via `StartService`/`ControlService`/`QueryServiceStatus`, not raw process fork/exec (which stays the POSIX-only mechanism). This is a real, standard pattern for a thin Windows service wrapper, and it is genuinely available before login since virtual service accounts have no session dependency.

**Exhaustion cleanup, corrected after round 8 (finding: a detached, unwaited helper process is not reliably survivable across any of the three platforms' own process/job/cgroup teardown on service stop — checked against each platform's real primitive this round, not assumed):** the wrapper's own restart-loop stop is the one guarantee made with full confidence on all three platforms — it exits with status code 0 on exhaustion, and every native restart setting this plan specifies (macOS `KeepAlive={"SuccessfulExit": false}`, Linux `Restart=on-failure`) restarts on a non-clean exit only, so a status-0 exit stops the loop immediately with no detached-process race. Full, unattended *file-level* deregistration is scoped per platform rather than claimed uniformly: on **Linux**, the unit file configures `ExecStopPost=<cleanup-helper>` — systemd's own real, supported post-stop hook, run by systemd itself as part of the unit's own stop sequence rather than a process the wrapper spawned and hoped would outlive it — and the wrapper writes a small `exhausted: true` marker just before its exit that the `ExecStopPost` helper checks to decide whether to also run `systemctl disable` and delete the unit file (an ordinary stop or `shutdown` leaves no such marker, so the helper does nothing extra). On **macOS and Windows**, no equivalent native post-stop hook exists; the wrapper's guarantee on these two platforms is limited to the immediate, always-reliable loop-stop above — the plist/scheduled-task registration itself remains present but dormant (it will not restart anything, since `RunAtLoad`/its boot trigger only fires at the next actual boot, at which point the same bounded 5-attempt-then-stop sequence simply repeats harmlessly) until a human runs `rush uninstall` (P68-06, which *can* synchronously wait and fully remove it, since it is a separate, human-invoked process) or a fresh `rush install` re-registers over it.

The wrapper artifact is kept separate from, and immutable relative to, the user-writable `rush` binary specifically so that ordinary use of the installed tool never grants a path to root-level code execution (round-5 finding R5-01's fix).
