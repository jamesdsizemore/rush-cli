## 1. Goal and boundary

After one consented project setup, a fresh supported coding agent discovers Rush without a prompt reminder, obtains an authorized bounded current-context packet, uses relevant evidence, records permitted decisions/outcomes at meaningful events, and allows a different agent to continue from current source and exact memory revisions. A user sees the true activation and recovery state in CLI, TUI, and dashboard. Claude Code, Codex, Cursor, Antigravity CLI (`agy`), and ZCode Agent (`zai` host lane) each retain an explicit acceptance lane. Z.AI as a model/API provider is distinct from ZCode Agent; provider selection alone never establishes a coding-host adapter.

Scope includes F09–F14, A01, B01–B04, E01/E13–E15, R04/R17/R20, AD01–AD04, TC05/TC09, AP02–AP06, activation part of AP07, and real-agent AP08. Phase 73 also carries the Phase 70 native packaging, setup, CLI/TUI, and Phase 71 dashboard activation obligations that make this outcome observable. Phase 72 owns canonical defensive reads, authorization/visibility, memory administration and human search; Phase 74 owns broader AST/workflow learning; Phase 75 owns full token accounting and benchmark repair. Those are narrow shared edges, not whole-phase prerequisites. Ordinary relevant preference, UI-system and architecture records must be delivered and corrected with their existing authority; deeper code-linked inference belongs to Phase 74.

Non-goals: new memory store, separate agent runtime, model training, universal transcript surveillance, Git hooks, silent global installation, auto-approval of native trust, release/publish, and claims that Rush can repair a host that withholds model-callable tools. No requested host, UI, or cross-agent outcome is excluded by these implementation boundaries.

### Fixed public and wire contract for 73-T09

`rush_memory(operation="capsule", request={...})` is the sole implementation entry. `request.action` is exactly `preview_export|export|preview_import|import|bridge`; `request.format` is exactly `rush_v1|pas_v1` (default `rush_v1`). CLI `rush memory capsule ACTION --project PATH --format rush_v1|pas_v1 --input FILE --output FILE --max-bytes N --max-tokens N --mapping-id ID --expected-digest SHA256 --expected-store-revision N --instructions FILE --confirm-constraint-id ID --apply --json` routes through the same `MemoryTool.run` and strict request parser as MCP. Default `--project` is current directory, `--max-bytes` is 65536 and `--max-tokens` is 8192; both are positive and may be lowered. A user may explicitly approve larger values in the request/preview/apply flow; never raise them automatically. Hard parsing caps are 1048576 aggregate bytes and 131072 rendered tokens, with nesting/record limits below unchanged. Above a hard cap, fail before effects and offer an explicitly narrower task rather than silent loss. `preview_export`/`export` require `--output`, reject `--input`; `preview_import`/`import` require `--input`, reject `--output`; `bridge` requires `--input` and `--instructions`, rejects `--output`, and uses `request.apply=false`/CLI without `--apply` for no-write preview, `true`/`--apply` for byte-checked write. `import` requires `--apply`; other actions except bridge reject it. `preview_import` and `import` accept repeatable `--confirm-constraint-id` / `request.confirm_constraint_ids: list[str]`, default empty, selecting exactly the constraint IDs whose applicability the user will approve. Preview remains non-authorizing. Apply must repeat the preview's selected IDs and digest; unknown, changed or omitted consent selection conflicts. Empty selection imports constraints as pending. Confirmation establishes applicability only, not verification of reported progress. `--expected-digest` is required for `export`, `import` and bridge apply from their corresponding preview; `--expected-store-revision` is additionally required for `import`. Preview digest is SHA-256 of canonical preview fields binding normalized apply-intent action (preview_export maps to export; preview_import maps to import), format, source file/store revision, scope/mapping, selected record set, `confirm_constraint_ids`, explicit byte/token limits and target pre-state (including an explicit absent-file marker); apply rechecks every bound input. `--mapping-id` is optional only when source and current canonical project/worktree identities already match. `--instructions` names an explicit file; no filename inference or automatic host-wide write. Action-inapplicable flags, unknown fields, mixed legacy/new request shapes and null-versus-omitted ambiguity fail before effects. `preview_*` and bridge preview never create store, lock, output, parent directory or authorization file. `export`, `import` and bridge apply need their respective current C01/C02 read/write/file permissions; file output is atomic, contained and refuses changed destination bytes absent matching preview. CLI help and MCP schema list exact actions, formats, required fields and limits. `--memory-session` restricted receiver remains restricted to existing operations; it does not gain `capsule`.

`rush_v1` file is deterministic UTF-8 JSON, `schema_version: 1`, `format: "rush_v1"`; required top-level fields are `capsule_id`, `created_at`, `origin`, `scope`, `task`, `evidence`, `manifest`, `payload_sha256`. `origin` contains producer Rush version, canonical source project/worktree IDs, source Git commit/branch/dirty state and snapshot store revision. `scope` contains approved owner and source labels as **descriptive metadata**, never grants. `task` contains description/objective, completed and remaining work, exact next action, constraints, decisions, failed approaches, blockers, discoveries, and last verified checkpoint with its check command/result/source revision. Constraint entries are `{constraint_id,text,origin_ref}`; IDs are stable within the capsule. PAS constraints receive deterministic IDs from SHA-256 of source session ID, constraint JSON pointer and exact UTF-8 text, retaining the original list order. `evidence[]` contains selected exact artifact ID/version/content hash/subject/source/owner/provenance/freshness plus required body or bounded source excerpt and its SHA-256; relative source path and source revision identify code evidence. `manifest` names selected and omitted optional IDs, source-relative paths, private/local-only references, redactions, required-body coverage, mapping requirement, producer encoding/tokenizer basis and delivered/omitted byte/token counts. No absolute origin path is authoritative on another machine. `payload_sha256` is lowercase 64-hex SHA-256 of canonical JSON of every other top-level field (sorted keys, UTF-8, no insignificant whitespace); it detects accidental/unauthorized byte change but is not a signature or proof of sender identity. Whole output is bounded at 65536 bytes and 8192 rendered tokens by default; parser caps nesting at 16, evidence at 128 records, checkpoints at 10 and file changes at 50 per checkpoint. Exceeding a cap returns an explicit error, never truncation of mandatory data. Reject duplicate JSON keys, unknown schema/format, invalid Unicode, path traversal/symlinks escaping selected root, digest mismatch, malformed required fields, over-size input and decompression/archive formats. Preserve Unicode text exactly; deterministic serialization does not normalize or rewrite user content.

Mandatory offline contents are task, next action, still-applicable explicit constraints, blockers/unresolved obligations, decision and failed-approach provenance, last verified check evidence, and every source/evidence body necessary to perform the named next action without access to origin store. Optional details can be omitted only with ID, reason and authorized retrieval route in `manifest`; local/private handles never satisfy a mandatory offline fact. No credentials, capability tokens, grant/binding IDs, personal/private records outside approved export scope, or secret-bearing excerpts appear in JSON, PAS output, Markdown bridge, errors or telemetry. Run scope, source/owner eligibility and secret filtering **before** serialization; on an unredactable mandatory fact, fail with a named exclusion and no output. A missing mandatory body or insufficient whole-file/render budget is a named minimum-budget/export error, never a truncated success. Phase 75-T03/T04 count complete JSON and derived Markdown, including wrapper, IDs, manifest and recovery text; unknown tokenizer basis is an estimate with margin, never an exact token guarantee.

Import validates complete file bytes/hash and every item hash before any write. `preview_import` reports origin, local candidate project/worktree, mapping ID and approval state, freshness/current-source checks, exclusions, contradictions, exact proposed typed writes, expected store revision, file digest and idempotency identity. `import` rechecks current grant/owner/source, approved mapping, current store revision and unchanged preview digest under CAS; writes atomic new typed records with original origin/provenance and `imported_unverified` authority, never overwrites concurrent records or promotes claims. Replay of same invocation and digest returns same receipt; changed bytes or revision requires new preview. PAS- or Rush-imported constraints remain pending evidence until local user confirms applicability; the preview enumerates these constraints and one explicit confirmation during apply may cover the enumerated set without repeated per-item prompts. Imported text cannot override host/project instructions. Source/path equality at origin is not local freshness: a moved checkout, changed branch, absent file, dirty change or unvalidated source gives `freshness=unknown`. An explicitly consented local mapping ID from C01 setup may map one origin project/worktree pair to one canonical target pair; a request flag or capsule field cannot approve its own remap. Local exact source hash/revision validation can separately advance freshness, then Phase 72's existing promotion route can consider authority. Offline read before import may guide a receiver only as labeled unverified material; it cannot establish managed `receiver_recalled` or verified continuation.

`pas_v1` codec targets pinned PAS-Agent [`0c9515a`](https://github.com/gfirik/pas-agent/blob/0c9515a6ec9bb32c3f33a93b3f981e283d211abd/crates/pas-agent-core/src/session.rs) `session.json` schema 1, not an invented PAS API. Exact top level: `schema_version`, `id`, `project_name`, `created_at`, `updated_at`, `task`, `git`, `checkpoints`. `task`: `description`, `objective`, `completed`, `remaining`, `next_action`, `blockers`, `decisions`, `constraints`, `discoveries`. `git`: nullable `branch`, nullable full `commit`, `dirty`. Each checkpoint: `id`, `timestamp`, `message`, `task_snapshot`, nullable `git`, `files_changed`; each file: UTF-8 relative `path`, `status`. Rust Serde's externally tagged `FileStatus` is JSON string `"Added"|"Modified"|"Deleted"|"Untracked"` or object `{"Renamed":{"from":"old/path"}}`; check renamed paths for containment and preserve both path bytes and Unicode. Preserve PAS UUIDs/timestamps/list order and explicit nulls. PAS has no native artifact provenance, failed-approach type, source-body, permission or verified-check field. Export writes a valid PAS JSON file **and** `<output>.rush-manifest.json` sidecar containing `schema_version:1`, `pas_sha256` over exact PAS file bytes, PAS session ID, bound `rush_v1` capsule digest, explicit field-by-field loss/unrepresentable ledger, retained Rush-only evidence and full `rush_v1` capsule. Import verifies PAS byte digest/session identity, Rush payload/item digests and their mapping before any write. Present but mismatched, stale or incomplete sidecars are errors, never silently treated as standalone PAS. Preview digest binds both files' exact bytes; mix-and-match valid files cannot pass. Preview binds both target pre-states; apply writes staged same-directory files with atomic per-file replacement and the sidecar as final commit marker. A crash between replacements leaves an incomplete pair, which Rush rejects and reports for recovery; no cross-file atomicity is claimed. Combined PAS file plus sidecar and complete rendered form meet the same byte/token bounds. Required task/constraint/decision/failed-approach/next-action meaning must remain intelligible in PAS's task fields; if it cannot be represented without false verification or truncation, reject export. A standalone foreign PAS file may be previewed/imported as limited, unverified task claims with absent Rush evidence declared; it cannot satisfy full offline capsule or strict round-trip acceptance. PAS codec does not execute PAS, install it, write `.pas-agent/session.json` implicitly, or treat PAS checkpoint/Git metadata as proof of completed work. Unknown PAS schema versions and unsupported statuses/fields fail explicitly. Round-trip tests compare meaning and provenance through the sidecar; no silent field drop.
