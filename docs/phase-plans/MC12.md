# MC12 — Add configured embeddings and deterministic hybrid ranking

Implements a new `src/rush/memory/embeddings.py` (`EmbeddingConfig`, `embed_chunks()`,
`validate_embedding_response()`, `EmbeddingEngineUnavailable`/`EmbeddingResponseError`),
`hybrid_candidates()`/`hybrid_page()`/`embedding_text()` in `src/rush/memory/retrieval.py`,
the additive `memory_embeddings` schema plus `scope_artifacts()`/`get_embedding()`/
`put_embedding()` in `src/rush/memory/store.py`, and `retrieval="hybrid"` wiring in
`MemoryTool._compact_query` (`src/rush/tools/memory.py`).

## Schema

`memory_embeddings` is one additive table appended to `_SCHEMA_SQL` after MC11's
`_HANDOFF_TABLES_SQL` (verified-by: `git diff` on `store.py` shows only the new
`_EMBEDDING_TABLE_SQL` constant inserted and `+ _EMBEDDING_TABLE_SQL` appended to the
`_SCHEMA_SQL` concatenation — every prior `CREATE TABLE`/`CREATE INDEX`/`CREATE TRIGGER`
statement, including MC01/MC02/MC03/MC10/MC11's, is byte-identical to before). Primary key
is `(namespace, artifact_id, artifact_version, content_hash, model_digest,
chunking_version)`: any of the last four changing is a cache miss, never a silent reuse of
a stale vector. `namespace` is `str(project_root)`, matching every other store table's
single-namespace-per-DB convention.

## Embedding adapter (`embeddings.py`)

`embed_chunks()` POSTs to `{endpoint}/api/embed` via stdlib `urllib.request`, batching at
most 32 inputs per request, `truncate=false`, a 10-second timeout, and a 1 MiB response
cap. `EmbeddingConfig.model_digest` is caller-asserted (the `/api/embed` contract has no
digest field to verify against) and is used purely as a cache-key component — no implicit
model pull ever happens. `validate_embedding_response()` rejects: a body that fails to
parse (covers truncation), a vector count that doesn't match the batch size, an
inconsistent or wrong (`expected_dimension`) vector dimension, a non-finite value, and a
zero-norm vector. Any connection failure/timeout raises `EmbeddingEngineUnavailable`
(engine missing); a validation failure raises `EmbeddingResponseError` — both are treated
as "hybrid unavailable" upstream, never surfaced as a partial hybrid success.

## Hybrid ranking (`retrieval.py`)

`hybrid_candidates()` scopes candidates two ways before ranking: `store.search_candidates()`
(MC02's existing lexical/BM25 path, reused unchanged) for the lexical rank, and the new
`store.scope_artifacts()` (same subject/source/trust/expiry filters, no FTS match required)
for the vector-candidate pool — this is what lets a semantic paraphrase with zero shared
terms still be found. A denied source is excluded from both scopes before any content is
ever assembled into an embedding batch (§6.7 "never send denied content to the embedding
endpoint"). Cached vectors are looked up per `(artifact_id, artifact_version, content_hash,
model_digest, chunking_version)`; only cache misses are sent to `embed_fn`. Fusion uses
`1/(60+lexical_rank) + 1/(60+vector_rank)` (absent rank contributes 0), sorted descending by
score with ID-ascending tie-break. `hybrid_page()` wraps this into the same page shape
`recall_page()` returns (no cursor — the candidate pool is already bounded to 512, a
documented ponytail ceiling), and falls back to a `recall_page()` result labelled
`code: "E_EMBEDDING_UNAVAILABLE"`, `retrieval: "lexical"`, `embedding_status: "skipped"`,
plus `hybrid_unavailable_reason` when no engine is configured or it's unreachable/invalid.

## Fix: hybrid-unavailable envelope conformance (post-review correction)

**What was wrong.** The original fallback branch of `hybrid_page()` returned `code="OK"`
(outer `status="ok"`), `data.retrieval="lexical_fallback"`, and never set an
`embedding_status` field at all. `test_missing_engine_reports_lexical_fallback_explicitly`
asserted that wrong shape as if it were the correct contract, so the defect passed review
undetected until an adversarial re-read of the plan caught it.

**What the plan required.** §9.0 fixed contracts (`docs/phase-plans/phase-63-memory-
capabilities-vibecoder-plan.md` line 245, exact literal text): "An unavailable hybrid
attempt with usable lexical results returns warn/E_EMBEDDING_UNAVAILABLE,
data.retrieval="lexical" and data.embedding_status="skipped"." §6.7 additionally requires:
"Bound vector candidates to 512 and report candidate truncation" — the 512 bound
(`_VECTOR_SCAN_CAP`) was already enforced, but nothing reported when a scan actually hit it.

**What changed.**
- `tools/memory.py`'s `_CODE_STATUS` map gained `"E_EMBEDDING_UNAVAILABLE": "warn"` (§9.0
  status/code pairs), so the outer `ToolResult.status` is now `"warn"` for this case instead
  of `"ok"`.
- `retrieval.py`'s `hybrid_page()` fallback branch now sets `fallback["code"] =
  "E_EMBEDDING_UNAVAILABLE"`, `fallback["retrieval"] = "lexical"`, and
  `fallback["embedding_status"] = "skipped"`; `hybrid_unavailable_reason` is kept as an
  additive detail field alongside these, unchanged.
- `hybrid_candidates()` now computes `candidates_truncated: bool` — `True` when either the
  lexical (`search_candidates()`) or vector-scope (`scope_artifacts()`) scan returned a full
  `scan_limit` (512) batch, mirroring `recall_page()`'s own `scanned >= _SCAN_CAP` cap-hit
  detection (§6.7's required consistency). `hybrid_page()` forwards this as
  `data.candidates_truncated` on every returned page (including the empty-allowlist and
  no-candidates early returns, where it is always `False`).

**Exact new field values (hybrid-unavailable case).** Outer envelope: `status="warn"`,
`raw["code"]="E_EMBEDDING_UNAVAILABLE"`. `data`: `retrieval="lexical"`,
`embedding_status="skipped"`, `hybrid_unavailable_reason=<engine failure detail>`, plus the
usual `recall_page()` fields (`items`, `next_cursor`, `complete`, `tokens`, `bytes`,
`encoding`).

**Test correction.** `test_missing_engine_reports_lexical_fallback_explicitly` now asserts
the corrected contract directly (`page["code"] == "E_EMBEDDING_UNAVAILABLE"`,
`page["retrieval"] == "lexical"`, `page["embedding_status"] == "skipped"`, and — through
`MemoryTool.run()` — `result["status"] == "warn"` and `result["raw"]["code"] ==
"E_EMBEDDING_UNAVAILABLE"`). A new
`test_candidate_truncation_reported_when_scan_cap_hit` exercises `hybrid_candidates()`
directly with an artificially small `scan_limit=1` against two real candidates to assert
`candidates_truncated is True` (and `is False` under the real default cap), then confirms
`hybrid_page()` forwards `candidates_truncated=False` for the untruncated default case.

`MemoryTool._compact_query` accepts `retrieval: "hybrid"` (`_RETRIEVAL_MODES`), requires
`network` (`E_PERMISSION` otherwise), and reads `embedding_endpoint`/`embedding_model`/
`embedding_model_digest`/`embedding_chunking_version` from the request (config.py wiring is
MC14's responsibility per §8.1; MC12 only consumes explicit per-call values). Vector
persistence is additionally gated on `granted.cache_write`, exactly like MC04's existing
telemetry gate.

## Exact ranking values (RED → GREEN evidence)

Fixture (`test_rrf_order_is_deterministic`): query `"widget"`; A2 content `"widget widget
widget"` (source `allowed`); A1 content `"widget"` (source `allowed`); D1 content `"denied
widget content"` (source `denied`, not in `session_allowlist`). Real `search_candidates()`
call returns lexical order `[A2, A1]` (A2's higher term frequency ranks it first; verified
directly against a live `TypedArtifactStore` before writing the test). Injected fixed
vectors give cosine order `[A1, A2]` (query vector `[1,0]`; A1 embeds to `[1,0]` → cosine
1.0; A2 embeds to `[0,1]` → cosine 0.0).

Fused scores, computed with `lexical_rank = {A2: 1, A1: 2}`, `vector_rank = {A1: 1, A2: 2}`:

```
score(A1) = 1/(60+2) + 1/(60+1) = 1/62 + 1/61 = 0.032572...
score(A2) = 1/(60+1) + 1/(60+2) = 1/61 + 1/62 = 0.032572...
```

Equal (asserted via `pytest.approx` in the test). The ID-ascending tie-break places `A1`
before `A2`; `hybrid_candidates()`'s real return was asserted (not inferred) to be exactly
`["A1", "A2"]`, identically on two consecutive calls (determinism).

## Denied-source assertion

`test_denied_source_never_sent_to_endpoint` records every text batch actually passed to
`embed_fn` and asserts `embedding_text(d1_content) not in sent_texts` — D1's exact canonical
embedding text never appears in any adapter call, because `scope_artifacts()`'s
`source_allowlist=["allowed"]` filter excludes it before the candidate/text dictionaries are
even built. `test_rrf_order_is_deterministic` uses the same fixture and omits D1's text from
the fixed-vector dict entirely, so any accidental inclusion would raise `KeyError` inside
the fake adapter rather than silently passing.

## Invalidation and read-only behavior

`test_model_digest_change_invalidates_vectors` (real `TypedArtifactStore`, fake
adapter — no network) verifies, in order: (1) a fresh embed populates `memory_embeddings`
under `digest-v1`; (2) a second call with the same digest/content reuses the cached vector
(adapter call count increases by 1, the query only, not 2); (3) switching to `digest-v2`
with unchanged content is a cache miss (adapter called again) and both `digest-v1` and
`digest-v2` rows coexist unmodified; (4) a direct-SQL content change under `digest-v1`
(mirroring the existing `test_memory_retrieval.py` raw-row test convention) is also a cache
miss — the old content-hash row is untouched and the new content-hash row is absent until
re-embedded. `test_read_only_hybrid_never_persists_vectors` asserts `cache_write=False`
leaves `SELECT COUNT(*) FROM memory_embeddings` at `0` and `store.get_embedding(...)` at
`None` after a successful hybrid ranking call — the vector is used for that call's ranking
only, never written.

## Real embedding-engine evidence

**Blocker (external, not a code defect):** no Ollama-compatible `/api/embed` endpoint is
running in this execution environment, and standing repository/task rules forbid installing
or starting new network services without explicit approval. All seven required tests
(§ above) exercise the real `validate_embedding_response()` parsing/validation logic and the
real `TypedArtifactStore`/SQLite cache path against fixed, injected vectors via an
injectable `embed_fn` — no network mock server, no monkeypatched HTTP layer — but
`embed_chunks()`'s actual `urllib.request` POST path itself has not been exercised against a
live engine in this task. A real-engine run requires: an operator-provided Ollama (or
compatible) instance reachable at a configured endpoint, an explicit embedding model pulled
there beforehand (no implicit pull, per §6.7), and `network`+`cache_write` grants — none of
which this task is authorized to stand up. Owner for closing this blocker: MC13 (real
provider/agent episodes) or an explicit follow-up task with an operator-supplied endpoint.
