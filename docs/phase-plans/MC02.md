# MC02 — Implement bounded recall and exact expansion

Evidence record for Phase 63 workstream MC02 (`docs/phase-plans/phase-63-memory-capabilities-vibecoder-plan.md` §9, MC02.1-MC02.5). Owned production files: `src/rush/memory/store.py`, `src/rush/tools/memory.py`, `src/rush/memory/retrieval.py` (new). Owned test file: `tests/test_memory_retrieval.py`.

## Schema additions (`store.py`)

Three additive pieces, alongside MC01's existing `artifact_version`/`memory_artifact_versions`/`memory_changes`, none of which are touched:

- `memory_fts_candidates` — a **second**, additive FTS5 external-content table (`content='memory_artifacts', content_rowid='rowid'`) with the §9.0 fixed six columns in order: `title, symbol_path, error_signature, behavior_id, dependency_identity, body`. The pre-existing single-column `memory_fts` table (used by `search()`/`recall()`) is never touched — legacy ranking/behavior can't regress by construction, not just by test coverage.
- Three triggers (`memory_artifacts_candidates_ai/ad/au`) keep `memory_fts_candidates` in sync with every `memory_artifacts` INSERT/UPDATE/DELETE, mirroring the existing `memory_fts` triggers' external-content delete/insert pattern. Contextual columns are extracted from `content` via `json_extract`, guarded by `json_valid()` so a malformed `content` value degrades to an empty contextual field instead of aborting the write (this is what makes a "corrupt candidate" possible to seed at all without breaking insertion).
- `memory_cursor_key(id INTEGER PRIMARY KEY CHECK (id=1), key BLOB NOT NULL)` — one random 256-bit key per store, created via `INSERT OR IGNORE` inside `_init_db()` (write-authorized construction only; `open_readonly()`'s `mode=ro` connection would simply fail that `INSERT`). `TypedArtifactStore.cursor_key()` exposes it to `retrieval.py` for HMAC-signing `recall_page()` continuation cursors.

`TypedArtifactStore._backfill_candidate_fts()` indexes any rows that pre-date `memory_fts_candidates` (mirrors `_migrate_version_column`'s additive-migration idiom), gated in `_init_db()` on whether the table already existed before that call's `executescript()`, so it only ever runs once per store's lifetime.

**SQLite pitfall found and worked around:** a plain (non-`MATCH`) `SELECT` against an external-content FTS5 table fails with `OperationalError: no such column: T.title` when the FTS5 table's declared column names don't match the backing content table's real column names (here, `memory_artifacts` has no `title`/`symbol_path`/etc. columns) — reproduced directly against a throwaway `:memory:` DB before landing the fix. `_backfill_candidate_fts()` therefore reads `memory_artifacts` directly and does per-row `INSERT OR IGNORE` into `memory_fts_candidates`, never a `SELECT ... FROM memory_fts_candidates` or a `WHERE rowid NOT IN (SELECT rowid FROM memory_fts_candidates)` subquery.

## `search_candidates()` (`store.py`)

`search_candidates(subject, query, *, source_allowlist, trust_tiers=None, include_expired=False, scan_offset=0, scan_limit=64) -> list[sqlite3.Row]` filters subject/source-allowlist/trust-tier/expiry in SQL `WHERE`, before `ORDER BY bm25(memory_fts_candidates, 4.0, 8.0, 8.0, 6.0, 3.0, 1.0) ASC, ma.id ASC LIMIT ? OFFSET ?` (lower BM25 score first, artifact ID ascending as the deterministic tie-break, matching §9.0 exactly). `query` is wrapped as a literal FTS5 phrase (`"..."`, embedded quotes doubled) so operator/quote characters in a caller-supplied query can't be interpreted as FTS syntax. Reads via `fetchmany(scan_limit)`, never `fetchall()` — the compact-recall path never materializes more than one 64-row batch at a time. An empty `source_allowlist` returns `[]` immediately (fail-closed).

**Deviation — "repository namespace" is not a separate filter column.** §9.0 describes candidate-query scope as including "repository namespace"; there is exactly one `memory.db` per project root in this codebase (`TypedArtifactStore.__init__`'s `db_path`), so the whole store already *is* the namespace — there is nothing to filter by. `search_candidates()` does not accept a `namespace` parameter. `recall_page()`'s cursor still binds `str(store.project_root)` as its namespace value (see below), so a cursor genuinely can't be replayed against a different store even though there's no per-row column.

## `recall_page()` / `expand_artifact()` (new `retrieval.py`)

Both return a plain `dict` with a leading `"code"` key (`"OK"` or a §9.0 warn/fail code) rather than raising, so `rush.tools.memory.MemoryTool` can map `code` straight onto `ToolResult.status` via the §9.0 status/code pairs table.

**`recall_page`** pages `search_candidates()` into a token/byte-bounded result:
- Scans up to 512 candidates *for this call* (the scan cap resets to 0 on every `recall_page()` invocation, whether or not a `cursor` continues an earlier scan position).
- A corrupt candidate (content that fails `json.loads` or isn't a JSON object) is skipped, not raised — it still counts toward the 512-candidate scan cap, but never blocks a valid candidate behind it from reaching the page (`test_corrupt_candidates_do_not_starve_page`).
- Per-item budget check: before appending a candidate, the *full* page payload (`items`, `next_cursor`, `complete`, `encoding` — no `next_cursor` yet known at this point, so `None`/`True` placeholders are used for the trial measurement) is serialized and measured against `max_bytes`/`max_tokens`; the candidate is only appended if the trial still fits. Final `tokens`/`bytes` in the returned page are measured after `next_cursor`/`complete` are known, so they're always exact.
- `complete=False` (with a `next_cursor`) only when the scan cap was hit *and* neither the page's own `limit` nor its byte/token budget had already finished the page first — reaching `limit`/budget exactly as the cap is hit still returns `complete=True` (§9.0: "until budget/limit is filled **or** a 512-candidate scan cap is reached").
- The cursor is `base64url(json payload) + "." + hmac-sha256(payload)`, HMAC-signed with the store's `cursor_key()`. The payload binds `subject, query, sorted(session_allowlist), str(project_root), ranking_version, generation (memory_changes' MAX(sequence) at the first call), scan_offset`. On a continuation call, an invalid signature, a decode failure, any binding mismatch (subject/query/allowlist/namespace/ranking version), or a live `current_generation()` that no longer matches the cursor's recorded generation all fail identically closed to `"E_RESTART"` with empty `items` — never partial/stale data.
- An empty `session_allowlist` returns `complete=True`, `items=[]` (matches `TypedArtifactStore.recall()`'s existing fail-closed precedent) rather than an error.
- A budget too small to fit even an empty page (`{"items":[],"next_cursor":null,"complete":true,"encoding":...}`) returns `"E_BUDGET"` before any candidate is scanned.

**`expand_artifact`** returns a base64-encoded byte slice (`content_base64`) of one stored artifact version's *exact* original bytes (from `memory_artifact_versions.content`, never re-serialized), starting at `offset`:
- Visibility is re-checked against the artifact's **current** row (`store.get_current()`), never an earlier `recall_page()` snapshot: a missing artifact and a denied `source` both return identical `"E_NOT_VISIBLE"` bodies (§9.0: "Missing and denied artifact IDs return identical E_NOT_VISIBLE bodies") — verified field-for-field equal in `test_revoked_or_changed_version_cannot_expand`.
- Only the artifact's *current* `artifact_version` may be expanded; a caller holding a since-changed version gets `"E_VERSION"`.
- The byte slice's length shrinks geometrically (`chunk_len -= max(1, chunk_len // 4)`) until the serialized `{"content_base64":...,"next_offset":...,"complete":...,"encoding":...}` payload fits both `max_bytes` and `max_tokens`; concatenating `content_base64` across pages (following `next_offset` until `complete`) reconstructs the stored bytes exactly, even when a page boundary lands mid-way through a multi-byte UTF-8 character (transmitted as base64, never as a raw/partial UTF-8 string) — verified with `café 中文 emoji 🙂` content across 18 pages at `max_bytes=100` (see example below).
- A budget too small to fit even an empty chunk returns `"E_BUDGET"`, `content_base64=None`.

Token counts use `tiktoken.get_encoding(encoding)` — the same real tokenizer `scripts/benchmarks/memory.py` already uses for `cl100k_base`, not the heuristic `FastBPETokenCounter` — since the default `encoding` value is itself `"cl100k_base"` and the reported `tokens` field needs to mean what its name says.

## `MemoryTool` wiring (`tools/memory.py`)

`request: dict[str, Any] | None = None` added to `__call__`/`run()`. Existing `ask`/`recall`/`list` calls with `request=None` (i.e. every pre-MC02 caller) take the unmodified `_query()` path — zero lines of that path changed. Only when a caller passes `request` does `_compact_query()` run: validates `request` has no unknown keys, `view == "compact"`, `retrieval` is `"lexical"` (hybrid is MC12, not implemented), and field types, then calls `recall_page()` and wraps its result as `{"schema_version":1,"operation":<op>,"code":<code>,"data":{...page fields...}}` in `ToolResult.raw`, with `status` set from the §9.0 status/code table.

`expand` is a new `MemoryOperation` (`request` required, fields `id`/`version` required, `offset`/`max_tokens`/`max_bytes`/`encoding` optional per §9.1's public request table) wired the same way through `_expand()`/`expand_artifact()`.

## Exact page/expansion examples (from live runs against a real `TypedArtifactStore`)

**Compact page**, 2 allowed + 1 denied artifact, query `"needle"`:

```json
{
  "code": "OK",
  "items": [
    {"id": "a1", "version": 1, "excerpt": "needle alpha", "source": "allowed", "trust": "IMPORTED", "freshness": "fresh", "relations": []},
    {"id": "a2", "version": 1, "excerpt": "needle beta", "source": "allowed", "trust": "IMPORTED", "freshness": "fresh", "relations": []}
  ],
  "next_cursor": null,
  "complete": true,
  "tokens": 87,
  "bytes": 323,
  "encoding": "cl100k_base"
}
```
The denied artifact (`source="denied"`, ranked ahead by BM25 since its text repeats "needle" more) never appears — excluded in `search_candidates()`'s SQL `WHERE`, not filtered after the fact.

**Scan cap continuation**, 513-candidate corpus, `limit=10000, max_tokens=1000000, max_bytes=1000000`:

```
page 1: complete=False, next_cursor=<hmac-signed>, items=512
page 2 (cursor=page1.next_cursor): complete=True, items=1
```

**Scope/generation restart**, same cursor reused:
```
session_allowlist changed  -> code="E_RESTART"
cursor tampered (1 char)   -> code="E_RESTART"
a write happens elsewhere, same allowlist, same cursor -> code="E_RESTART"
```

**Unicode expansion**, content `"café 中文 emoji 🙂 " * 40` (1762 stored bytes), `max_bytes=100`:
```
18 pages returned (code="OK" every page); b"".join(all content_base64, base64-decoded) == stored bytes exactly.
```

**Revoked/version-changed expansion:**
```
expand(id="a1", version=99)                -> E_VERSION  (never matched current version)
update_content(a1) then expand(version=1)  -> E_VERSION  (now-stale version)
expand(id="d1" [source=denied])            -> E_NOT_VISIBLE, content_base64=None
expand(id="nope" [missing])                -> E_NOT_VISIBLE, content_base64=None (identical body to the denied case)
```

**Legacy compatibility** (`request=None`): `ask`/`recall`/`list` still return `{"status": "ok", "raw": [<artifact dict>, ...], "metadata": {"operation": "ask"}, ...}` with no `schema_version`/`code`/`data` keys anywhere in the response — verified directly in `test_legacy_memory_response_remains_compatible`.
