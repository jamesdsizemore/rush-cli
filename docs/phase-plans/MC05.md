# MC05 — Capture observations and expose real sandbox verification

Evidence record for Phase 63 workstream MC05 (`docs/phase-plans/phase-63-memory-capabilities-vibecoder-plan.md` §9, MC05.1-MC05.5). Owned production files: `src/rush/invocation/executor.py`, `src/rush/invocation/models.py`, `src/rush/invocation/resolver.py`, `src/rush/cli_support/rendering.py`, `src/rush/mcp_support/tool_registry.py`, `src/rush/tools/memory.py`, `src/rush/config.py`, `src/rush/catalog.py`, `examples/rush.toml`, `docs/reference/configuration-reference.md` (observation opt-in config only); new `src/rush/memory/experience.py`, `src/rush/memory/verification.py`. Owned test files: `tests/test_memory_observations.py`, `tests/test_memory_verify_attempt.py`.

## What MC05 adds

MC01-MC04 (versioning, bounded recall, relations/consolidation, dedup+telemetry) are unchanged and untouched by MC05: `store.py`'s `_write_version`/`write()`/`recall()`/`search_candidates()` and `retrieval.py`'s `defended_recall()`/`recall_page()`/`expand_artifact()` are only ever *called*, never duplicated or bypassed. MC05 adds two new things on top:

1. **`record_observation`** (`src/rush/memory/experience.py`): a single canonical observer, invoked from `InvocationExecutor.execute()` after a handler returns and before the result-cache write, that normalizes a completed `InvocationContext` + tool result into one `experience`/`episodic` `MemoryArtifact` and persists it through the existing `TypedArtifactStore.write()` path.
2. **`verify_attempt`** (`src/rush/memory/verification.py`): a real memory operation, wired into `MemoryTool` (`operation="verify_attempt"`), that applies a caller-declared patch inside the existing `PatchSandboxManager` sandbox and runs the existing `PatchVerifier.verify_patch()` against a caller-declared `PatchContract` — never a new sandbox/verifier implementation.

## The single opt-in config key (MC05.2)

`[tools.memory] record = true|false` (default `false`) is the *only* `tools.memory` configuration key MC05 adds; MC14 adds the remaining `tools.memory` keys later. It flows through the same generic per-tool-option machinery every other tool already uses:

- `catalog.py`: `TOOL_SPECS["memory"].option_specs` gains one `ToolOptionSpec(name="record", value_type=bool, default=False, ...)`.
- `config.py`: `resolve_memory_record(cfg)` reads `cfg["tools"]["memory"]["options"]["record"]` (the shape `_snapshot_config()` produces for a real `RushConfig`), falling back to a flat `cfg["tools"]["memory"]["record"]` for a raw test-style config dict. Default `False` either way.
- `invocation/models.py`: `InvocationContext` gains one new field, `memory_record: bool = False`.
- `invocation/resolver.py`: `resolve_invocation()` calls `resolve_memory_record(cfg)` once and threads the result into the new `InvocationContext.memory_record` field — never derived from result text or a caller-declared flag.
- `examples/rush.toml` and `docs/reference/configuration-reference.md` document the key with its default.

**Deviation (recorded, not silent):** `mcp_support/tool_registry.py`'s `make_tool_wrapper`/`make_custom_wrapper` never loaded `rush.toml` at all before MC05 — only the CLI path (`cli_support/rendering.py::_run_tool`) did (`load_config(start=path)`). Since `memory_record` must resolve identically on both transports for `test_observer_covers_cli_mcp_without_duplicates` to hold, both MCP wrapper functions now call a small `_load_config_or_none(root)` (same `load_config(start=root)` the CLI already uses) and pass the result into `resolve_invocation(..., config=...)`. A malformed `rush.toml` fails open to no config there (`RushConfigError` caught, `config=None`) rather than newly breaking every MCP tool call over a config error MCP never validated before — this is strictly additive to MCP's existing config posture, not a narrowing of it.

## The observer route (MC05.1/MC05.2)

```
InvocationExecutor.execute(context)
    operation.handler(*args, **kwargs)              # the real tool call, unchanged
    if context.memory_record
       and "cache_write" in context.permissions
       and context.operation_id != "memory":
        rush.memory.experience.record_observation(context, result)   # try/except, never raises
    (existing result-cache write, unchanged)
    return result                                     # exact original identity, always
```

`record_observation` excludes `operation_id == "memory"` a second time internally (belt-and-suspenders against the generic per-invocation observer ever recursing into the memory tool's own reads/writes/verify_attempt calls). A cache **hit** returns before the handler ever runs, so it structurally never reaches the observation call — no special-casing needed for "cache hit produces no new execution-success record" (`test_cached_result_keeps_original_execution_identity`).

All three transport entry points named in the plan converge on this one `InvocationExecutor.execute()` path with zero duplication, proven directly in `test_observer_covers_cli_mcp_without_duplicates`:

| Transport entry | Call in test | Observation asserted |
|---|---|---|
| CLI | `rush.cli_support.rendering._run_tool("probe", cli_root, as_json=True, permissions=ExecutionPermissions(cache_write=True))` | exactly 1 row, `operation_id="probe"`, `transport="cli"` |
| MCP (catalog tool) | `rush.mcp_support.tool_registry.make_tool_wrapper(tool, executor)(mcp_root, allow_cache_write=True)` | exactly 1 row, `operation_id="probe"`, `transport="mcp"` |
| MCP (custom/phase tool) | `rush.mcp_support.tool_registry.make_custom_wrapper(fn, "custom-probe", executor)(custom_root, allow_cache_write=True)` | exactly 1 row, `operation_id="custom-probe"`, `transport="mcp"` |

Each entry uses its own isolated `tmp_path` subdirectory with its own `.rush/memory.db`, so "without duplicates" is asserted per-transport (exactly one row each) rather than one shared count across all three.

## Normalization and evidence (MC05.3)

`record_observation` builds one content payload per execution: `schema_version`, `kind="observation"`, `evidence_kind` (one of five capability families, below), `operation_id`, `request_id`, `transport`, normalized `targets`, `workspace_root`, `effective_config_digest`/`environment_digest`/`artifact_build_identity`/`tool_revision`/`normalizer_revision` (exact source/patch/config/environment identities per §6.4), `ordered_args`/`declared_ignored_inputs` (preserved, not summarized), the result's `engine`/`engine_version`/`status`/`summary`/`metadata`/`raw`, and `conditions` (granted permissions + cache policy). It is written via `MemoryArtifact(family="experience", subject="episodic", trust_tier=default_entry_tier("local_tool"), ...)` — reusing MC01's exact family/subject vocabulary, never a parallel table.

**Five explicit capability families** (`classify_capability_family`, from the vibecoder-integrations assessment's "Where the rest of Rush contributes" table, R14-R17): `tests_contracts` (tests/contracts/snapshots/E2E/mutation), `source_graph` (codegraph/API-diff/coverage), `security_dependency` (security/dependency/license checks), `sandbox_verification` (sandbox/patch verification/provenance), `continuity_checkpoint` (continuity/checkpoints/token utilities). `test_five_capability_families_preserve_evidence_kind` is parametrized over one representative operation per family (`test`, `api-diff`, `security`, `patch-apply`, `continuity`) and asserts the classifier's answer is exactly what lands in the persisted `content["evidence_kind"]`. Unmapped operations fall back to `sandbox_verification` (most Rush tools ultimately execute and report a command outcome — the closest generic family), never raise.

**Secret redaction precedes persistence, with no window:** `write_observation()` never redacts anything itself — it hands the raw content straight to `TypedArtifactStore.write()`, which is where `sanitize_value(artifact.content)` already runs, immediately before the SQL `INSERT`. There is exactly one place secret content is ever serialized to disk, and redaction happens there unconditionally. `test_secret_redaction_precedes_persistence` plants an AWS-shaped key (`AKIA...`) inside a tool result's `raw.stdout`, calls `record_observation` directly, and asserts the raw secret string is absent from both the returned artifact's content *and* a fresh `SELECT content FROM memory_artifacts WHERE id = ?` read straight off disk — while `[REDACTED_AWS_ACCESS_KEY]` is present in both.

**Failure preserves original identity:** `test_failed_observation_preserves_original_tool_failure` runs a tool that returns `status="fail"` through the real `InvocationExecutor.execute()` route with recording on and `cache_write` granted, and asserts the executor's return value is the exact unmodified failing result *and* the recorded observation's `content["status"] == "fail"` — the observer never rewrites, retries, or launders a failure into a success.

## `verify-attempt`: real sandbox execution, never inferred success (MC05.3/MC05.4)

`rush.memory.verification.verify_attempt(attempt_id, behavior_ids, repo_root, contract, patch, granted, declared_permission_names=())`:

1. Requires `cache_write` + `artifact_write` + `build` unconditionally, plus every permission the caller explicitly names in `declared_permission_names` (`network`/`download`/`slow`/`browser`) — **never inferred from the declared check commands themselves**. Missing anything -> `outcome="denied"`, and `PatchSandboxManager.create_sandbox()` is never called (no `.rush/worktrees` directory is ever created for a denied attempt).
2. Creates a real `PatchSandboxManager(repo_root).create_sandbox()` git worktree, applies `patch` with the existing `PatchApplier.apply_patch_to_dir()`, and runs the existing `PatchVerifier(sandbox_path, contract=contract).verify_patch()` — the same drift-checking, command-executing verifier MC/Phase 58 already ships, not a reimplementation.
3. On `PatchVerificationError` (base commit/tree drift) the attempt is caught and reported as `outcome="failed"` with **no observation written** for that attempt (there is no real `PatchVerificationResult` to report truthfully) — a rejected drift attempt can never accumulate fabricated "completed" evidence.
4. On a real `PatchVerificationResult` (`completed`/`failed`/`unavailable`), `write_observation(evidence_kind="sandbox_verification", ...)` finalizes exactly one observation carrying the attempt's real `executed_commands`, `passed_count`, and `outcome` — truthfully, including `unavailable` (zero executed commands) and `failed` (checks ran and failed).
5. `finally: manager.cleanup_sandbox(sandbox_path)` always tears the sandbox worktree down, whatever branch was taken. Never promotes, never touches `repo_root`'s own working tree, never auto-commits, never auto-rolls-back source.

`MemoryTool.run(operation="verify_attempt", request={attempt_id, behavior_ids, contract, patch, declared_permissions})` (`tools/memory.py`) validates the request shape, converts `contract` (JSON) into a real `PatchContract` via `verification.parse_patch_contract()` (raises on a malformed command entry rather than silently building an empty plan), and maps the outcome onto `ToolResult.status`: `completed -> ok`, `failed -> fail`, `unavailable|denied -> skipped` — never `ok` for anything but a genuine `completed` outcome.

### Exact command -> receipt path (`test_verify_attempt_runs_real_command_in_sandbox`)

A fixture git repo commits one buggy module (`upload.py`, ignores both a timeout and a size-limit check) and a real check script (`check_upload.py`) that asserts both behaviors. Two attempts run against two different unified-diff patches, both through the *real* `sys.executable check_upload.py` command inside the sandbox (not a mock):

1. **Partial-fix patch** (fixes only the timeout branch) -> real subprocess exits 1 (the size-limit assertion still fails) -> `outcome="failed"`, `executed_commands[0]["exit_code"] != 0`.
2. **Full-fix patch** (fixes both branches) -> real subprocess prints `OK` and exits 0 -> `outcome="completed"`, `executed_commands[0]["stdout"]` contains the real `"OK"` process output.

After both attempts: `repo/upload.py`'s bytes, HEAD, and tree digest are byte-identical to before either attempt ran; `git status --porcelain` on `repo_root` is empty; `git worktree list` shows no leftover `sandbox_*` entries (both worktrees were torn down, no leaked children). A third attempt through `MemoryTool().run(operation="verify_attempt", ...)` (the full wiring, not the bare function) reproduces the same `completed` outcome and the same unchanged-checkout guarantee.

### The other two named tests

- `test_verify_attempt_rejects_drift_and_missing_permissions`: (a) `ExecutionPermissions()` (nothing granted) against a well-formed contract -> `outcome="denied"`, zero sandboxes created, zero observations; (b) a contract whose `base_commit` is `"0"*40` (a real 40-hex-char SHA that cannot match) against a real sandbox -> `PatchVerificationError` raised by the real `PatchVerifier`, caught, `outcome="failed"`, zero observations recorded for that specific attempt ID (no fabricated evidence for a rejected drift). Source checkout is asserted unchanged after both.
- `test_unavailable_check_never_records_success`: an empty `required_commands=()` contract against a sandbox with no auto-detectable project markers (no `pytest.ini`/`tests/`/`package.json`/`Cargo.toml`) -> the real `PatchVerifier` executes zero commands -> `outcome="unavailable"`, `executed_commands == ()`, `passed_count == 0` -- and the one observation that *is* written for this attempt carries `outcome="unavailable"`, never `"completed"`.

## Deviations

- `mcp_support/tool_registry.py` now loads `rush.toml` per MCP invocation (previously never loaded any config) — see "The single opt-in config key" above.
- `MemoryTool.__call__` gained `allow_artifact_write`/`allow_build`/`allow_network`/`allow_download`/`allow_slow`/`allow_browser` parameters (previously only `allow_cache_write` existed) so `verify_attempt`'s wider permission set is reachable from both CLI and MCP transports, matching the existing convention other multi-permission tools (e.g. `mutation.py`) already use.
- `tools/memory.py`'s import of `rush.memory.verification` is function-local (inside `_verify_attempt`), not module-level: `rush.memory.verification` imports `rush.patch.applier`, which imports `rush.tools.common`, which triggers `rush.tools.__init__`, which imports `rush.tools.memory` itself — a genuine circular import at module-import time that a lazy import breaks cleanly (the same lazy-import pattern `invocation/executor.py` and `config.py` already use elsewhere in this codebase).
- One additional test beyond the required list, `test_verify_attempt_rejects_unknown_contract_field`, asserting `parse_patch_contract` raises `KeyError` on a command entry missing `"command"` rather than silently producing an empty plan.
