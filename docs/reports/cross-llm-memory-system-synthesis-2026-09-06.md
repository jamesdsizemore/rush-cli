# Cross-LLM Memory System — Synthesis

Answers the research goal in `cross-llm-memory-system-plan-2026-09-06.md`, built from the 41 individual `/repo-evaluator` reports in `~/repo-reports/`. Per-repo evidence lives in those reports; this file is the verdict and the composition.

## Verdict: synthesis, not wholesale

No single repo of the original 41 covers the required scope. The three highest-scoring repos — `oceanbase/powercontext` (90), `vectorize-io/hindsight` (90.4), `zilliztech/memsearch` (90.3) — are each strong on 3-4 of the 7 memory/context subjects, not all 7, and none ships as a directly-importable Python 3.12 library with zero adaptation. **`hindsight` was independently re-verified against its actual source code after an initial misread — its "embeddable, no server" claim is false (it spawns a detached daemon running a full FastAPI/Postgres service and can silently `curl | bash` an installer); only its `MemoryDefenseExtension` write-time gate survives as a citation, cited below.** The system has to be built from named pieces across multiple repos. Below is that composition, piece by piece, with the source repo and file cited for each.

A second round of 13 additional repos (11 newly evaluated + 2 reused from the original 41) was checked with the same code-first standard applied to every "embeddable/no-server" style claim before acceptance, not just hindsight's. None of the 13 covers all 7 subjects either — this confirms the synthesis verdict rather than changing it. Two results from this round materially improve specific component choices, folded in below: `riponcm/projectmem` and `agentic-box/memora`. Full findings for all 13 are in their individual `~/repo-reports/` files.

A third round of 20 additional repos was evaluated the same way (see table near the end of this document). One, `dev-boz/gitmem`, was initially reported as "near-wholesale, covers 6 of 7 subjects" — that claim was independently re-verified against its actual source and did not hold up: the real count is 3 of 7 (episodic, skill/pattern, active-context have real code; preference, failure/mistake, architectural-decision, and domain-knowledge do not), the specific subject the initial report called "missing" (active-context) is actually one of its best-implemented pieces, and the project is single-maintainer and dormant (no push in 3 months). This is recorded here as a correction, not silently fixed — the second-round independent-verification step exists specifically to catch this class of error before it reaches a build decision.

## Cross-tool transport (the actual "drop-in" mechanism)

Two layers, not one, because tools vary in how much structure they support:

**Corrected after independent verification — see the adversarial-review section near the end of this document.** The original version of this section proposed engram's adapter pattern as the primary transport and flagged ACP as an under-researched option. Both were wrong in specific, checked ways. Current, verified design:

1. **Native SDK first, per tool that has one** — for Claude Code, Anthropic's official Python `claude-agent-sdk` (PyPI); for Codex, OpenAI's native `codex app-server` protocol (JSON-RPC over stdio, Python client available). Both independently confirmed to exist and be first-party, structured, and directly Python-reachable with no adapter hop.
2. **ACP for tools that natively implement it** — confirmed real, published, multi-vendor standard (Zed Industries + JetBrains, official Python SDK `agent-client-protocol` on PyPI) — but Claude Code and Codex are **not** among the tools that implement it natively; they're only reachable through third-party translation adapters (`claude-agent-acp`, `codex-acp`) that wrap the same native SDKs in (1). Tools confirmed to implement ACP natively: Gemini CLI, GitHub Copilot CLI, Goose, Cline, OpenHands, and others. Use ACP for exactly this tier — tools with no better first-party Python-reachable protocol of their own — not as a blanket first choice.
3. **Config-bootstrap adapters (one-time setup, not runtime transport)** — `Gentleman-Programming/engram`'s `engram setup <tool>` pattern is real and independently verified (12 genuine, tested, non-stubbed adapters). But it solves a different problem than rush has: every adapter writes a static config file once at install time that the target tool discovers at its own next startup — none of them hand data to a running instance at invocation time. This is legitimate prior art for rush's own one-time `rush setup <tool>` bootstrap step (replacing a hardcoded list with a registry), but it is not a transport tier and should not be described as one.
4. **Universal prompt-block fallback** — `VictorTaelin/OptMem`'s convention (append to `AGENTS.md`/`CLAUDE.md`, read by anything that honors that file convention, zero per-tool code) for any tool with neither a native SDK nor ACP support. No license exists on OptMem itself — idea-only, reimplement the convention.

## Trust/governance layer (replaces rush's binary quarantine flag)

This is the most important structural change relative to rush's current design. `continuity/receipts.py` today marks everything non-current as `"authority": "historical_evidence", "state": "quarantined"` — one bit, binary. Composition, cited per piece:

- **Write-time gate**: `vectorize-io/hindsight`'s `MemoryDefenseExtension` (`hindsight_api/extensions/memory_defense.py`) — real, verified ALLOW/REDACT/BLOCK screen run on every write, independent of caller identity.
- **Cheap first-pass filter ahead of the gate above**: `ThreatRecall/zettelforge`'s `prompt_injection_guard.py` — deterministic regex against instruction-override/exfiltration-style patterns, cheap enough to run on every write before the heavier anomaly check.
- **Trust taxonomy replacing the binary flag**: `mnemosyne-oss/mnemosyne`'s `TRUST_TIER_MAP` (`mnemosyne/core/beam.py`) — `STATED`/`DERIVED`/`EXTERNAL_WRITE`/`IMPORTED`, mapped at ingestion by source. This is the direct replacement for rush's single `"quarantined"` state.
- **Read-side scoping** (separate concern from write-gating): `plastic-labs/honcho`'s `session_allowlist` pattern (`src/dialectic/core.py`) — fails closed on empty input, restricts which sessions' memories are recall-eligible.
- **Memory-internal audit, independent of host tool**: `rohitg00/agentmemory`'s `src/functions/governance.ts` — bulk delete requires explicit IDs or explicit filter, records an audit trail regardless of which tool issued the call.
- **Identity-forgery lesson**: `NevaMind-AI/memU`'s ADR 0015 — proves a content-based self-identification marker is forgeable by injected memory; identity must be verified from invocation-environment signals, never from a string inside the data itself. Applies directly to whatever marks a memory record as "authoritative" in the new design — that marker cannot itself live inside attacker-reachable content.

Governed by the split established in the plan's governance section: **read/recall ungated by rush's code-permission layer** (but scoped by the honcho-style allowlist), **write-as-authoritative gated** by the hindsight/zettelforge/mnemosyne composition above, not by rush's `ExecutionPermissions`.

## Answering the three research-goal questions

**1. Context-vs-memory, both required, working together:** Partially answered by `oceanbase/powercontext`'s `Handoff`/`Experience`/`Memory`/`Skill` typed-artifact family, corrected after independent verification (see adversarial-review section). The four families are real, genuinely decoupled from any framework, and a reasonable schema *shape* to adopt — but the "general enough to hold all 7 subjects" claim does not survive: 2 of 7 (episodic/session memory, and failure/mistake as a first-class concept) have no dedicated field or kind anywhere in powercontext's own code. Rush would be defining new `kind` values into powercontext's unconstrained free-text field, not reusing an existing taxonomy for those two — the schema *container* is reusable, the *coverage* claim was overstated.

**2. Anti-injection tension:** Answered by the trust/governance layer above — moves rush from one binary flag to a real write-time defense gate plus a multi-tier trust taxonomy, both with working precedent, not invented from scratch.

**3. Genuine provider-agnosticism, not a fixed list:** Answered by the corrected transport-tier design above (native SDK → ACP → prompt-block fallback, per tool) — replacing rush's current hardcoded provider dict with a per-tool tier lookup, not a single mechanism.

## Migration path from rush's current memory code

Rush's current `memory/`/`continuity/` code doesn't get thrown away — it maps onto the new typed-artifact model directly:

**Corrected after independent verification of powercontext (see adversarial-review section):** `kind` on `Memory`/`Experience` is an unconstrained `str` in the persisted schema, not an enum — the values below are rush defining its own taxonomy inside a generic container, not reusing one powercontext already models. `preference` and `decision` have loose existing precedent in powercontext's own LLM-extraction prompt vocabulary; `failure` has none at all. Also: powercontext's `trust` field on `Handoff` is a `Literal` with exactly one possible value (`"untrusted_history"`) that nothing in its own code branches on — it's a type-safe label, not an enforced gate. Adopting `mnemosyne`'s 4-tier enum means rush has to build the actual enforcement itself; powercontext doesn't supply a pattern for that beyond the field existing.

- `preference_store.py` → becomes a filtered view over `Memory` records tagged `kind=preference`.
- `invariant_graph.py` → becomes `Experience` records tagged `kind=architectural_decision`.
- `failure_ledger.py` + `mistake_miner.py` → merge into `Experience` records tagged `kind=failure` — a new kind rush defines, not one powercontext models today. Keep `failure_ledger.py`'s SHA-256 fingerprint-hash dedup mechanism as-is — it's the right idea, it just moves under the unified schema instead of its own standalone table.
- `checkpoint_journal.py` → becomes `Handoff` records — this fits powercontext's own use of `Handoff` as a bounded, disposition-tagged continuation snapshot. `session_memory.py` (full turn-by-turn episodic history) does **not** fit `Handoff` the same way — powercontext has no episodic/session family at all (independently confirmed: zero hits for `episodic`/`session_memory` anywhere in its source). This needs its own new artifact family, not a fit into an existing one; rush's `trust` enum (`STATED`/`DERIVED`/`EXTERNAL_WRITE`/`IMPORTED`, replacing today's single `"quarantined"` string) is rush's own design to build and enforce, informed by `mnemosyne`'s pattern, not inherited from powercontext.
- `continuity/receipts.py`'s `save_receipt`/`restore_receipt` collapses into the `Handoff` serialization boundary — a receipt IS a handoff; there's no need for two separate concepts.
- **Storage engine: move off CAS-JSON files (`transactions.py`) onto one SQLite WAL database** implementing the typed-artifact schema. Rush already proves this pattern works in `failure_ledger.py` (real SQLite, real concurrent-safe usage) — this is also what ADR-0030 originally claimed but never actually built. Given multi-agent coordination already exists (`continuity/coordination.py`'s mesh lock manager), SQLite+WAL is the correct choice over flat-file CAS for concurrent typed-artifact writes.

## Transport tier decision (corrected — see adversarial-review section)

The original version of this section committed to ACP as an unconditional tier 1, citing `rowboatlabs/rowboat` as precedent. Independent verification found that framing backwards: rowboat needed third-party ACP adapters (`claude-agent-acp`, `codex-acp`) specifically *because* Claude Code and Codex don't speak ACP natively — both are reachable more directly through their own first-party SDKs, which is what those adapters wrap internally anyway. Citing rowboat as justification for "ACP is tier 1" actually demonstrates the opposite for the two tools named.

Corrected tiers, per tool, not a single blanket protocol: **(1) native SDK/protocol** where the target tool has one (`claude-agent-sdk` for Claude Code, `codex app-server` for Codex) — lower-latency, no adapter hop, both independently confirmed to exist and be Python-reachable. **(2) ACP** for tools that implement it natively (Gemini CLI, GitHub Copilot CLI, and others — confirmed real adoption, not rowboat-specific) and have no better first-party option. **(3) Prompt-block fallback** (`OptMem`'s pattern) for anything with neither. Rush's transport dispatcher checks per-tool which tier applies — it is not "try 1, then 2, then 3" for every tool, since which tier is even available differs by tool.

## Write-promotion rule (not left open)

New memory enters at trust tier `EXTERNAL_WRITE` or `DERIVED` by default (never `STATED`). Promotion to `STATED` (authoritative) requires all of: (a) passes `hindsight`'s ALLOW/REDACT/BLOCK screen, (b) passes `zettelforge`'s regex pre-filter, (c) the record's typed schema fields are fully populated, not partial (`akitaonrails`' validation pattern), and (d) either the user stated it directly (promotes immediately) or it's been independently derived/observed at least twice (corroboration threshold of 2). This is a concrete rule, not a reference to go adapt later.

## License handling (not left open)

No literal source from `basicmachines-co/basic-memory` (AGPL-3.0) or `plastic-labs/honcho` (AGPL on the server) gets copied into rush-cli — pattern/idea only, same as every other repo in this synthesis. `VictorTaelin/OptMem` has no license file — also idea-only. This isn't a pending decision; it's the methodology this whole synthesis already used throughout, restated so it's not missed.

## Enhancement ideas beyond the core 7-subject design

These extend the design above using rush-cli capabilities that already exist (verified by reading the actual source, not assumed) rather than proposing anything disconnected from the real codebase. This is a starting list, meant to grow.

- **Code-anchored memory, not free-floating text.** Rush already has `memory/merkle_invalidator.py` (AST content-hash staleness detection) and `codegraph/context_packer.py`/`traverser.py`. Architectural-decision and failure/mistake memories should anchor to the actual symbol/file they're about, so when that code changes, the memory flags itself stale automatically — the same mechanism codegraph already uses for blast-radius tracking, applied to memory instead of just code.
- **A query interface (`rush memory ask`), not just storage.** Same one-call, compact-structured-answer shape as `codegraph_explore`/`graft ask`, backed by the write-promotion/trust design above.
- **Memory as a token-savings layer in front of existing compression, not a separate concern.** Rush's `token_economy/` (`ccr_store.py`, `cache_aligner.py`, `stale_sweeper.py`) already compresses/caches/sweeps raw content. A durable-memory check before an expensive AST-pack — "do we already have an answer for this" — sits in front of that pipeline as a cache rush doesn't have yet.
- **Review and development actually reading memory, not just storing it.** Rush's core is a 124-engine review CLI with ADRs/governance. A review finding checking failure/mistake memory before reporting ("this pattern already caused a fix in commit X"), or a planning step checking architectural-decision memory ("this was already decided in ADR-0030"), changes what review and development *do* — not just what they log.
- **Per-tool skill/hook bundles generated from the transport-tier spec already written above**, the way `engram setup <tool>` generates per-tool config (verified this session) — but pointed at rush's own memory backend instead of a third party's.
- **A maintenance sub-agent using rush's existing mesh-lock coordination** (`continuity/coordination.py`) to own the write-promotion rule, the skill-candidate admission gate (pattern verified in `scope-recall-hermes`'s `skill_bridge.py` above), and staleness sweeps as bounded, reversible background work — not a human-run cron job.
- **Provenance for memory records, reusing infrastructure rush already built for a different purpose.** Rush generates cryptographic SLSA Level 3 build provenance (`cryptography` is a pinned core dependency for exactly this). The same signing machinery applied to memory records — an attestable chain of who/what asserted a memory, when, with what evidence — turns memory into a signed artifact instead of a plain row, at low added cost since the capability already exists.
- **Governance-drift detection against rush's own ADR sync.** `governance/synchronizer.py` (confirmed real) syncs ADRs/rules across IDEs. When a rule changes, diffing it against stored architectural-decision memories that assumed the old version and flagging the contradiction turns memory into an active drift-detector against rush's own governance system, not a passive store sitting next to it.
- **Handoff diffs instead of handoff blobs.** Rush's current cross-provider handoff (`continuity/receipts.py`/`providers.py`) sends a full state snapshot every time. For a workflow that bounces between tools repeatedly in one session (the core scenario this whole project is for), sending a diff against the *last* handoff to that same tool instead of a full snapshot directly cuts tokens on exactly that workflow. This is new relative to the transport-tier design above, which specifies how a handoff reaches a tool, not how much of it needs sending each time.
- **Memory-driven regression-test suggestions.** Rush ships its own benchmark harness (`scripts/benchmarks`, in the packaging manifest). A mined failure/mistake memory with no covering test becomes an actionable trigger to generate one — connects memory to rush's testing identity directly, not just review.
- **An attribution trail for AI-made changes.** `session_memory.py` already tracks tool_name/finding_count/fixes_applied per turn. Extending that into a queryable link from a git commit/diff hunk back to the specific decision-memory and failure-memory records that informed it is real "why did the agent do this" traceability, buildable from what already exists.
- **Team memory, git-native.** Git-tracked, PR-reviewable shared memory is a real, validated pattern from this session's research (`dev-boz/gitmem`, `oceanbase/powercontext`'s shared-pool concept) — made safe by the trust-tier gating already designed above. Rush's architecture decisions and failure ledger could live in a git-tracked folder the way ADRs already do, syncable across a team's rush installs — memory that outlives one user, not scoped to a single-player tool.
