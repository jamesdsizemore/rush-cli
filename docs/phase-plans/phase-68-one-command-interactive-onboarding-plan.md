# Phase 68 — One-and-Done Install

## 1. Why this phase exists

Real end-to-end testing this session (2026-09-13/14) found the actual path from "download rush" to "rush is checking my code" requires four separate typed commands, each with flags never documented anywhere a new user would find them:

```
curl -fsSL .../install.sh | sh
rush init .
rush governance sync
rush setup . --install --allow-download --allow-network --allow-build --allow-cache-write
```

Explicit requirement from the maintainer, verbatim, final: a user should only ever have to run one command (the install line itself, or `rush install` — never longer than two words) or click one button. That single action installs into the current project, activates and serves the MCP server, activates and serves all available CLIs, activates and serves the memory system, and launches the web dashboard. No picker, no prompt, no second command, no wizard.

**Extended requirement (2026-09-14):** the dashboard must stay reachable without the user doing anything again — not after closing the terminal session, and not after restarting the machine, including before that user logs back in. `rush install` registers a real, boot-level OS autostart entry: a `LaunchDaemon` on macOS, a system-level `systemd` unit on Linux, and a Windows Scheduled Task with a boot trigger, each described precisely in P68-05. Registering any of these three requires one elevated-privilege prompt during `rush install` (`sudo` on macOS/Linux, a UAC prompt on Windows) — that elevation is scoped to this one registration step, not the rest of install. The TUI (`rush ui`) is not part of this — it is a foreground interactive terminal program; there is nothing sensible to "autostart" about it. Only the headless dashboard server gets a persistent, boot-level autostart entry.

**Extended requirement (2026-09-14, round 2):** the install experience itself must be graphic, animated, engaging, and explanatory — a live, styled progress display naming each step as it runs, not a plain scrolling log. This does not reopen the "no picker, no prompt, no second command, no wizard" requirement: the whole run is still fully automatic and non-blocking end to end, including through `curl | sh` — piping a script into `sh` or a downloaded `pwsh` binary cannot read an interactive prompt from stdin regardless of what gets built here (established in §2 below), so nothing in this phase ever waits on typed input. The one real, unavoidable place a human has to act is the OS's own elevation dialog for boot-autostart registration.

**Process-ownership architecture, established after round-1 adversarial review (2026-09-15) — read this before any packet below:** an earlier draft of this plan never specified which process actually serves HTTP requests once boot-autostart exists, and had `rush install` reach into another process's in-memory Python objects across a process boundary, which is not possible. The design:

- **The OS-registered service process is the only thing that ever calls `server.serve_forever()`.** `rush install` itself never runs a long-lived server loop — it is a short-lived setup command that exits. Manually running `rush dashboard` (no `--service` flag) still runs its own separate, foreground `serve_forever()` loop exactly as it does today (`cli.py:1244`, unchanged by this phase) — the boot service and a manually launched dashboard are two independent, coexisting kinds of `create_dashboard_server` callers, not one replacing the other.
- P68-05 registers the service to run a new, dedicated **service-mode** entry point (`rush dashboard --service`, not the existing `dashboard_cmd` path, which prints the bootstrap URL to stdout unconditionally — see §2) on a stable port, and P68-05 also **starts that service immediately** after registering it, not only at the next boot.
- **P68-04 (the install-triggered scan) never touches an in-process registry.** `rush install` becomes an authenticated HTTP client of its own (already-running) dashboard, using the exact real auth/action contract checked against source this session and specified concretely in P68-04 below — not an invented shortcut. This is the only way a project registered by `rush install`'s own process can end up inside a different, already-running service process's state.
- **Credential handling is now precisely scoped, correcting round-1's overcorrection.** The constraint that no bootstrap/session secret may reach a log file applies specifically to the **service's own persistent log output** (`StandardOutPath`/`StandardErrorPath` / the systemd journal / the Windows task's redirected log) — a boot service's log is unattended, long-lived, and not something the installing user is watching in real time. `rush install` itself is a short-lived, foreground, user-attended terminal command: it may print its own one-time launch URL to its own stdout and open the browser automatically, exactly as `dashboard_cmd` already does today, without reopening the "no second command" requirement. What `rush install` never does is write that URL, bootstrap token, or session cookie to any *file* (a log, the progress-display state, the per-server descriptor) — only to its own interactive stdout, once, for the human already watching that terminal.

## 2. Current state, checked against source this session (do not re-derive, build on this)

- `scripts/install.sh` / `scripts/install.ps1` already download the binary and hand off to `rush install --agents all --memory on` as their last line. Passing no `--project` leaves project selection "pending" today (`src/rush/tools/install.py`; verified-by: read README.md's Install section and src/rush/tools/install.py this session) — this is exactly the gap P68-01 closes.
- **Engine provisioning is already wired.** `InstallTool.run` (`src/rush/tools/install.py:347-357`) already calls `run_setup_wizard(Path(project_view["root"]), install=True, permissions=granted, project_id=project_view["project_id"], ...)` unconditionally whenever `project_view is not None`. The only real gap is that `project_view` is `None` without an explicit `--project` today — P68-01's fix alone unblocks it. `_check_manager_available` (`src/rush/setup/provision.py:610`) can raise `SYSTEM_PREREQUISITE_REQUIRED`; P68-02 propagates that into overall install status.
- **`rush install`'s own binary self-replacement can conflict with a running boot service (verified-by: read `_atomic_install_binary`, `src/rush/tools/install.py:212-231`, and `InstallTool.run`'s call to it at `:427-442`, this session).** Every `InstallTool.run` call backs up and then `os.replace()`s the installed binary unconditionally. On POSIX, `os.replace` swaps the inode atomically, so an already-running boot-service process keeps its old code loaded in memory until restarted — the installer's new HTTP behavior silently does not take effect until a later restart. On Windows, `os.replace` (`ReplaceFile`) against a binary a running process has open can fail outright with a locked-file error, which `_atomic_install_binary` does not special-case — a repeat `rush install` while the boot service is running can hard-fail on Windows. P68-05 below adds explicit stop-before-replace/restart-after-replace handling.
- `rush mcp serve` (stdio MCP server) already exists, but there is no shared listening MCP daemon for `rush install` to "start once." `build_stdio_entry` (`src/rush/integrations/agents.py:158`) registers a command line each connecting agent launches as its **own** subprocess. `probe_agent_connection` (`src/rush/integrations/agents.py:737-753`, verified-by: read this session) "re-reads an agent's config off disk and reports its real current state" — it is a config-file check, not a live probe of an already-running client's transport. **No adapter in this repo has a live-transport verification mechanism today** — P68-03 below states this as a named limitation rather than assuming one exists.
- `rush dashboard` (`src/rush/dashboard/server.py`) already exists as a command. `create_dashboard_server` (`server.py:2116-2131`) only constructs and binds the HTTP server from a caller-supplied `projects` dict and **returns without calling `serve_forever()`** — `dashboard_cmd` (`cli.py:1134-1250`, read in full this session) is the only existing caller of the serving loop, and it: registers exactly **one** project (`register_project(resolved_path)`, the CWD), builds one empty snapshot for it, starts one scan for it, and prints the bootstrap URL to stdout unconditionally (`--no-open` only suppresses `webbrowser.open()`, not the print). A boot service that must serve **every** durably-registered project, not just the CWD one, cannot reuse this single-project pattern as-is — P68-05 below specifies real boot-time reconstruction.
- `ProjectRegistry` (`src/rush/dashboard/state.py:81-141`, read this session) is explicitly **per-server-instance**: constructed fresh from a caller-supplied `projects: dict[str, dict]` at `create_dashboard_server` call time, with no built-in mechanism to load from the durable, cross-session project registry. That durable registry already exists and is readable via `list_projects_page(limit=..., cursor=..., data_root=...)` (`src/rush/workflows/projects.py:400-...`, verified-by: read this session) — a paginated, HMAC-cursor-authenticated listing keyed off an explicit `data_root`. P68-05 below wires the service-mode entry point to page through this at startup and build the `projects` dict `create_dashboard_server` needs, instead of seeding a single project.
- `default_data_root()` (`src/rush/setup/provision.py:112-131`, verified-by: read this session) resolves per-OS from live environment state at call time: `$XDG_DATA_HOME` (Linux, falling back to `~/.local/share`), `%LOCALAPPDATA%` (Windows, raising `DataRootUnavailableError` if unset), or a fixed macOS path. A boot-time service process does not inherit the installer's interactive shell environment — if the user installed with a custom `$XDG_DATA_HOME` set, a service started with a bare/systemd-provided environment would resolve a *different* data root and see a different (likely empty) project registry. P68-05 below persists the resolved absolute data root at registration time and passes it explicitly to the service, never re-resolved from ambient environment at boot.
- **The real HTTP auth/action contract for an unattended client (verified-by: read `src/rush/dashboard/server.py:1620-1731` and `src/rush/cli.py:1058-1133`, and `tests/test_dashboard_scan_actions.py:76-267`, all this session):** a per-server descriptor file (written by `_write_dashboard_descriptor`, `cli.py:1058-1079`) carries `bound_host`, `bound_port`, and a `control_capability` token — the same descriptor `rush dashboard --reconnect` already reads via `_newest_dashboard_descriptor`. That bootstrap token is then exchanged via `POST /api/session` with `Authorization: Bearer <bootstrap_token>` (loose-Origin-checked) for a session cookie plus a CSRF token (`ctx.auth.exchange_bootstrap`, `auth.py:76-88`); every mutating call after that (`POST /api/projects`, `POST /api/projects/{id}/actions`) requires that cookie, an `X-Rush-CSRF` header matching the session's `csrf_token`, and an **exact**-match `Origin` header (`server.py:1658`, `require_exact=True`). Starting a scan is **not** a single `scan_start` call: `_dispatch_scan_start` (`server.py:408-447`) requires `arguments.plan_id` naming a plan that was already staged to disk by a prior `provision_plan` action (`_dispatch_provision_plan`, `server.py:362-373`, which calls `plan_scan` and returns `scan_plan.plan_id`) — an unstaged/unknown `plan_id` is rejected with `409`. ## 3. Scope

**In scope:** `rush install` (both as the installer scripts' handoff and as the command an existing install re-runs) does everything in one shot when run from inside a project directory with no arguments: registers the current directory as the project, detects its stack, writes `rush.toml`, syncs governance rules (when a canonical `AGENTS.md` exists), installs missing engines, connects every detected agent's CLI, activates memory, ensures a boot-level dashboard service is registered and running (starting it immediately, not waiting for reboot), and — as an authenticated HTTP client of that now-running service, using the real auth/action sequence in §2/P68-04 — registers the project against it and drives a real scan through to completion. The entire run displays as a live, styled, explanatory Rich progress sequence naming each step, reusing `THEME`/`MOTION`, never blocking on typed input anywhere. A companion `rush uninstall` stops the service and removes the autostart entry.

**Out of scope, explicitly not touched here:** the `--allow-*` permission-flag architecture shared by other CLI commands. `rush setup`, `rush init`, and `rush governance sync` remain available as standalone commands. `rush ui` (the TUI) is never autostarted. `rush uninstall` removes only the autostart registration and stops the service this phase adds — it never deletes registered projects, `rush.toml`, or memory data. System-wide, pre-boot, multi-user daemon behavior beyond P68-05/P68-06 is out of scope.

### P68-05 — Boot-level OS autostart registration, real multi-project startup, and immediate service start (macOS, Linux, Windows)

**stop_if:** on macOS, `codesign -dv --verbose=4 <binary>` shows signature presence only; `spctl -a -vv <binary>` reports Gatekeeper's real accept/reject/notarization verdict. If `spctl` does not report an accepted, notarized verdict, stop and get that resolved (this repo's release pipeline, a separate decision) before building the macOS half; Linux/Windows can proceed regardless.

**Service-mode entry point and startup, decided here:**

- `rush dashboard --service` (hidden option, not advertised in `--help`) is the command line every platform's autostart entry registers. It differs from ordinary `dashboard_cmd` in: never calling `webbrowser.open`; never printing a bootstrap URL/cookie/CSRF value to stdout or stderr; and, on startup, **reconstructing every durably-registered project** by paging through `list_projects_page(data_root=<the explicit root from registration, never re-resolved from ambient environment>)` and building the `projects` dict `create_dashboard_server` needs from that — not seeding a single CWD project the way `dashboard_cmd` does. An empty registry at boot (no projects registered yet) is valid and starts with zero projects, not an error.
- It tracks its own consecutive-crash count in a small state file next to the descriptor, exiting with a distinct "give up" status once that count crosses a fixed threshold (5). **This app-level counter is the secondary backstop, not the primary one** — it only ever runs if the Python process itself starts and then fails (e.g. a port conflict); it cannot run at all if the `rush` binary fails to execute (missing file, exec-format error, etc.), so the **primary** backstop for that case is each platform's own native bounded-restart setting, specified concretely below, not the app-level counter.
- **Data root persistence:** the absolute, resolved `default_data_root()` value is computed once, at registration time, inside `rush install` (which still has the installer's real environment), and passed explicitly to the service (as a plain, non-secret argument or an explicit env line in the platform's own service definition) — the service-mode entry point never calls `default_data_root()` itself at boot.
- **Binary replacement:** before `InstallTool.run`'s existing `_atomic_install_binary` call, check whether the boot service is currently running (via the descriptor); if the new binary's bytes are identical to the currently-installed one (hash compare), skip replacement entirely as a no-op; otherwise, if the service is running, stop it via the same real service-manager stop command P68-06 uses, replace the binary, then start it again via the platform's own "start now" primitive — never leave a running process holding stale code after a `rush install` re-run, and never attempt `os.replace` against a binary a running Windows process has locked.
