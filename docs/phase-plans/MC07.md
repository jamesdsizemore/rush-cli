# MC07 — Store confirmed intent and verify its behavior

Evidence record for Phase 63 workstream MC07 (`docs/phase-plans/phase-63-memory-capabilities-vibecoder-plan.md` §9, MC07.1-MC07.5). Owned production files: new `src/rush/memory/intent.py`, `src/rush/tools/memory.py`, `src/rush/memory/experience.py`. Owned test file: `tests/test_memory_intent.py`.

## What MC07 adds

MC01-MC06 are unchanged and untouched: `store.py`'s `write()`/`get_current()`/`get_version_content()`/`update_content()`/`promote()`, `trust.py`'s `default_entry_tier`/`evaluate_promotion` promotion gate, and `experience.py`'s existing `record_observation`/`write_observation`/`record_attempt`/`recall_repair_episodes` (MC05/MC06) are only ever *called* by MC07's new code, never duplicated or bypassed.

`src/rush/memory/intent.py` (new) adds:

1. **`record_intent`** — creates a new intent (a fresh `intent_id`, used directly as the `MemoryArtifact.id`) or re-records/confirms an existing one via `TypedArtifactStore.update_content()`'s existing compare-and-swap path. An inferred record (`statement_ref=None`) always stays `status="candidate"` — there is no `confirmed=` parameter anywhere in this module, so a caller can never assert its way past resolution.
2. **`supersede_intent`** — an explicit, distinct mutation for genuinely *changing* the recorded requirement (a new `behavior_id`/`statement_ref`, not just attaching evidence to the same one). Requires the exact current version (`expected_old_version`) and a *new*, resolvable, currently-`STATED` `new_statement_ref`.
3. **`check_intent`** — read-only: walks one intent's `check_refs`, and only ever trusts a referenced artifact that (a) is still at the exact version the ref recorded (a stale/superseded reference is silently skipped), (b) carries a real `ToolResult.status` or `VerifyAttemptOutcome.outcome` value (never a bare label/tag), (c) names the same `behavior_id`, and (d) — when `current_revision` is given — matches it exactly. Never launches a command.
4. **`intent_evidence`** — read-only aggregator (used by `prepare_memory`): the current intent record (refs only, never resolved evidence) for each requested `behavior_id`. Fails closed on an empty `behavior_ids` or `session_allowlist`, matching `recall_repair_episodes()`'s existing no-default-cross-session-access precedent.

`src/rush/memory/experience.py`'s `prepare_memory` now also calls `intent_evidence(project_root=project_root, behavior_ids=behavior_ids, session_allowlist=session_allowlist)`, adds the result under a new `"intent_evidence"` key, and folds its `{id, version}` pairs into the existing `evidence_refs` list alongside `failures`/`verified_repairs`/`untested_hypotheses`. No other part of `prepare_memory`'s contract changed.

`src/rush/tools/memory.py` wires a new `"intent"` `MemoryOperation` with a single `_intent` handler dispatching on `request["action"]` in `{"create", "confirm", "supersede", "check"}`: `create`/`confirm` call `record_intent` (both require `cache_write`, same gate as `write`/`promote`); `supersede` calls `supersede_intent` (also `cache_write`); `check` calls `check_intent` and requires no permission grant, matching the plan's §9.1 request table row ("`intent` | action, intent_id | mutation fields from MC07; check only needs ID | cache_write for mutations; none for check"). `_CODE_STATUS` gained one new mapping, `"UNRESOLVED": "warn"`, for `check_intent`'s unresolved-evidence code.

## Why one artifact per `intent_id`, mutated in place (not a new artifact + relations edge per supersede)

`relations.py`'s `supersedes` cycle check (`_supersedes_cycle_exists`) walks `memory_relations` by `artifact_id` alone, ignoring version. Modeling supersession as a *new* artifact ID linked to the old one via a `supersedes` relation edge works once — but a **second** supersede of the same lineage would create a same-ID self-loop in that traversal (`new_source == new_target` by ID across two different edges sharing an ID) and get rejected as a false cycle. Reusing the *same* `intent_id` and going through `TypedArtifactStore.update_content()`'s existing compare-and-swap avoids this entirely: `memory_artifact_versions` (MC01 §6.1's existing audit trail) already retains every prior version's full content forever, so "retain prior rationale/evidence, never delete history" is satisfied by infrastructure that already exists, with zero new bookkeeping and no relations-graph self-loop risk. This also makes `intent_evidence`'s per-behavior_id lookup trivial: `TypedArtifactStore.search()` only ever returns one *current* row per artifact ID, so there is never a duplicate/stale-shadow row to filter out.

## The authority rule, structurally enforced (MC07.2/MC07.4)

`_resolve_authorized_statement(project_root, statement_ref)` is the single choke point every mutation goes through: it resolves `statement_ref` to a `MemoryArtifact` only if `store.get_current(id).trust_tier == "STATED"` **and** its current `artifact_version` matches exactly. This structurally rules out every authority bypass named in the task, with no separate special-case check needed for any of them:

- **A caller-asserted `confirmed=True` flag** — there is no such parameter on `record_intent`/`supersede_intent`; status is always derived from resolution, never accepted as an assertion.
- **A newer agent timestamp** — `created_at` is never read by the resolver at all; only `trust_tier` and `artifact_version` matter.
- **An imported/inferred role label** — `default_entry_tier("cross_tool_handoff")` returns `"IMPORTED"`, `default_entry_tier("local_tool")` returns `"EXTERNAL_WRITE"`; neither is ever `"STATED"`, and `write()` itself refuses to insert `trust_tier="STATED"` directly (`TrustTierError`) — promotion via `store.promote(id, user_stated=True)` is the only path to `STATED`.

`test_agent_timestamp_cannot_supersede_user_intent` writes an `IMPORTED`-tier artifact with `created_at=time.time() + 10_000.0` (a "newer agent timestamp") and asserts `supersede_intent` returns `"E_PERMISSION"` and the original intent's version/content are completely unchanged. `test_inferred_preference_cannot_confirm_itself` shows the same resolution failing closed for a `record_intent` re-record attempt, not just supersession.

## Execution binds behavior, not labels (MC07.3/MC07.4)

`check_intent`'s `_execution_result()` only recognizes two truthful, already-executed vocabularies this repo writes into memory: `ToolResult.status` (`"ok"|"warn"|"fail"|"error"|"skipped"`, from `rush.tools.base.ToolStatus`) and `VerifyAttemptOutcome.outcome` (`"completed"|"unavailable"|"failed"`, from `rush.patch.contracts.PatchOutcome`, MC05's `verification.py`). A bare label/tag record (`{"kind": "trace", "tags": [...]}`) has neither key and is therefore never recognized as behavioral verification, regardless of what its tags claim.

`test_guest_checkout_break_detected_by_execution` records an original passing receipt (`status="ok"`, `revision="rev-a"`) and a regression receipt (`status="fail"`, `revision="rev-b"`) carrying the identical `"labels": ["guest-checkout-verified"]` metadata field — `check_intent(current_revision="rev-b")` returns `passed=False` because it is bound to the exact revision's real status, never the unchanged label. `test_trace_tag_is_not_behavioral_verification` records only a bare trace record as the sole `check_ref` and asserts `check_intent` returns `"UNRESOLVED"` — a resolvable artifact that isn't real execution evidence is never mistaken for proof. `test_intent_check_bound_to_current_revision` asserts a `current_revision` that matches no recorded receipt (`"rev-z"`) is `"UNRESOLVED"` even though a receipt for a *different* revision exists on the same intent — a stale receipt is never proof for the revision being asked about; omitting `current_revision` entirely returns whatever is resolvable, unbound.

## Explicit supersession never deletes prior rationale (MC07.2/MC07.4)

`test_explicit_user_change_supersedes_old_intent` creates a `guest-checkout-allowed` intent confirmed against a `requires_account=False` STATED statement, then supersedes it with a `new_statement_ref` pointing at a *different*, separately-promoted `requires_account=True` STATED statement and a new `behavior_id="account-required-checkout"`. The current row afterward carries only the new statement/behavior — but `store.get_version_content(intent_id, created["version"])` (the pre-supersede version) still returns the original statement/behavior byte-for-byte, proving the old rationale and evidence are retained, never overwritten or deleted.

## Distinct required-test walkthrough

| Test | What it proves |
|---|---|
| `test_inferred_preference_cannot_confirm_itself` | An intent with no `statement_ref` stays `candidate`; pointing `statement_ref` at a real, resolvable but non-`STATED` artifact (an imported/inferred record) also never confirms it. |
| `test_guest_checkout_break_detected_by_execution` | A regression is detected by real per-revision execution status, not by unchanged label/tag metadata. |
| `test_trace_tag_is_not_behavioral_verification` | A bare trace/tag record, though resolvable, is never accepted as behavioral verification — `check_intent` returns `"UNRESOLVED"`. |
| `test_explicit_user_change_supersedes_old_intent` | An explicit, newly-authorized statement supersedes the old requirement; the prior version's content is still readable, unmodified, in `memory_artifact_versions`. |
| `test_agent_timestamp_cannot_supersede_user_intent` | A newer agent timestamp on an imported (non-`STATED`) artifact cannot supersede; the intent is left completely unchanged. |
| `test_intent_check_bound_to_current_revision` | A revision with no matching receipt resolves `"UNRESOLVED"` even when evidence exists for a *different* revision on the same intent; omitting the revision filter still resolves the intent's real evidence. |

## Deviations

- **`record_intent`'s `behavior_id` is `str \| None`, not the plan's literal required field, so a `"confirm"` re-record can omit it and default to the currently-stored value.** A brand-new `intent_id` still requires it explicitly (`E_INPUT` otherwise) — this only relaxes the *re-record* path, where forcing every caller to re-state an unchanged `behavior_id` would invite an accidental silent overwrite instead of preventing one.
- **`intent_evidence` surfaces refs only (`statement_ref`, `check_refs`, `status`), never resolved `check_intent` evidence**, because resolving evidence requires a `current_revision` that `prepare_memory`'s existing signature has no field for. Extending that signature was out of scope for "include active relevant intent/check refs" specifically; a caller can always call `check_intent` directly per intent once a revision is known.
- **The MemoryTool "confirm" and "create" actions are both thin dispatches onto the same `record_intent` function**, distinguished only by whether the tool caller supplies `expected_version` (confirm/re-record) or omits it (create, on a brand-new `intent_id`). This is the same reuse relationship `prepare`/`resume` already have onto one `_prepare` handler (MC06) — not a new pattern.
